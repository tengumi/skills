# Извлечение командных подходов

Зафиксируй, как команда фактически строит проекты, чтобы новое решение
могло следовать подтверждённым образцам. В отличие от
[harness-scan](../harness-scan/SKILL.md), здесь нужно читать реализацию,
а не только проверять наличие файлов.

## Источники

Используй указанный набор репозиториев и `workspace.json`, если он существует.
Иначе найди проекты по файлам языка и зависимостей. Не включай окружения,
зависимости, кеши и сборки. Сгруппируй проекты по стеку.

Прочитай каждый проект выбранного набора; не выдавай выборку за полный анализ.
Не читай `.env`, значения секретов и итоговую конфигурацию с секретами.
Способ загрузки настроек определяй по коду, имена настроек отделяй от значений.

Для Python изучи зависимости, первые два уровня структуры, основной модуль,
настройки, журналирование, исключения, подготовку тестовых данных и пример теста,
Makefile и настройки проверки кода. Для Java — систему сборки, приложение,
контроллер, сервис, конфигурацию и тест. Для веб-интерфейса — зависимости,
команды, TypeScript, правила проверки, компонент и тест.
При необходимости посмотри последние 20 сообщений Git, не меняя историю.

## Что описать

- Размещение исходников, тестов, инструментов обслуживания и ресурсов.
- Зависимости и зафиксированные версии: модели, HTTP, конфигурация,
  журналирование, тесты и проверки кода.
- Именование файлов, классов, функций и тестов.
- Загрузка настроек, обязательность полей и обращение с секретами.
- Создание журнала, формат записей, уровни и допустимое содержание.
- Исключения, места их обработки, HTTP-ошибки, повторные попытки.
- Устройство агента: инструменты и их регистрация, входы/выходы, промпты,
  цикл выполнения, способ получения задач и состояние между вызовами.
- Организация тестов: внешние подмены, реальные компоненты, тестовые данные,
  интеграционные и асинхронные проверки.
- Соглашения Git, если они подтверждаются историей и правилами команды.

Для Java отдельно отрази слои, пакеты, передачу данных и обработчики ошибок;
для интерфейсов — компоненты, состояние, обращения к API и оформление.

Каждое наблюдение сопровождай значением, источниками, отклонениями и
`confidence`: `high` при согласованности не менее 70% исследованных проектов,
`medium` при 50–менее 70%, `low` при меньшей доле или смешанных несовместимых
подходах. Запиши размер выборки. Эти доли показывают распространённость,
но не доказывают качество или обязательность решения.

## Файлы результата

В корне обследуемой папки создай `team-patterns.json` с полями:

```json
{
  "extracted_at": "<дата>",
  "workspace_root": "<корень>",
  "sources_analyzed": [],
  "review": {
    "status": "pending",
    "approved_by": null,
    "approved_at": null,
    "approved_low_confidence": []
  },
  "python": {},
  "java": {},
  "frontend": {},
  "divergences": [],
  "coverage_gaps": []
}
```

Для Python используй разделы `project_structure`, `dependencies`, `naming`,
`config_pattern`, `logging_pattern`, `error_handling`, `agent_patterns`,
`test_patterns`, `git_conventions`. Сохраняй машинные имена полей, например
`source_dir`, `test_dir`, `approach`, `location`, `confidence`, `note`.
Значения должны происходить из кода; отсутствующие сведения отмечай явно.
Не копируй в результат версии и библиотеки из примеров этого или другого скилла.

В `team-conventions.md` представь те же наблюдения понятным русским: структура,
библиотеки и версии, именование, устройство агентов, ошибки, тесты и Git.
Отдельно покажи таблицу различий между проектами и нерешённые вопросы.
Отсутствие тестов — пробел, а не подтверждённое командное соглашение.

## Проверка человеком и применение

Всегда создавай `review.status: pending`. Не одобряй собственные выводы.
После проверки владелец устанавливает `approved`, заполняет `approved_by`
и `approved_at`; слабоподтверждённые решения отдельно перечисляет точными
путями JSON в `approved_low_confidence`.

Только после этого файл может направлять
[harness-template](../harness-template/SKILL.md). Официальный шаблон и документы
команды всё равно имеют приоритет. Распространённый устаревший код нельзя
переносить в новый сервис только потому, что он встречается чаще.

Проверь корректность JSON и соответствие обоих документов источникам.
В отчёте перечисли охват анализа, сильные и спорные наблюдения, созданные
файлы и необходимые решения. Не создавай задачи исправления и не меняй
исследованные репозитории без отдельного запроса.
