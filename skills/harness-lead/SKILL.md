# Ведущий маршрута Harness

Этот скилл выбирает следующий шаг, но не заменяет правила профильных скиллов.
Не записывай `harness-lead` в `tasks.json.use_skill`: у задачи должен быть точный
скилл реализации или проверки.

## Что нужно для запуска

- `prototype` — источник логики, доступный только для чтения.
- `target` — целевой репозиторий из командного шаблона.
- `team_template` либо подтверждение, что целевой репозиторий уже создан из него.
- `<harness_kit>` — указанный пользователем путь к рабочему комплекту `harness-kit-prom`, содержащему
  схемы `templates/`, документы `team-docs/` и сервер Tasks MCP.
  Рабочие программы самого скилла находятся в его `scripts/`.
  Определяй путь к ним относительно этого `SKILL.md`, не рабочего каталога.
- `target/docs/harness/pre-industrialization-spec.md` — паспорт подключений:
  операции, версии контрактов, адреса и имена настроек, способы авторизации,
  ссылки на секреты без значений, БД и реквизиты развёртывания. Доступные факты
  извлекай из кода и документов сам.

Если в целевом репозитории нет обязательных командных документов, передай точный
источник в `harness-context` как `team_docs_source`. Не перезаписывай существующие
файлы. Отсутствие паспорта не мешает этапу A: создай его из шаблона, а недостающие
сведения запроси перед зависящим от них подключением на этапе B.

Сохрани исходное разрешение на автоматические безопасные локальные изменения
как `safe_offline_authorization`, указав, откуда оно получено. Оно покрывает
согласованный план и избавляет от повторных вопросов, но не разрешает обращения
к реальным системам, изменения общей БД, выполнение миграций или развёртывание.

Используй `production_neighbour` и `release_reference` только если они явно
предоставлены. Командный пример помогает выбрать реализацию, но не заменяет
контракт. Не требуй прошлую реализацию этого агента и не ищи её по похожему имени.
Передавай примеры в `harness-extract-prod` и планировщик; исполнитель читает
только подходящий справочник `harness-production-readiness`.

## Определить текущее состояние

Прочитай применимые `AGENTS.md`, документы `docs/harness/` и состояние Git.
Не загружай всю историю и стабильные инструкции повторно без изменений.
Если `tasks.json` уже есть, получи актуальное состояние через
`tasks-mcp.list_open_tasks(repo_path, include_all=true)`. При `out_of_band`
файл хранит определения задач, а их текущие статусы находятся в Tasks MCP.
Если файла ещё нет, сначала создай минимальный контекст репозитория.

Проверь доступность прототипа, целевого репозитория и командного шаблона.
Зафиксируй версию прототипа: commit/tag либо воспроизводимый хеш значимых
файлов без кешей и результатов запусков. Отсутствие Git HEAD само по себе
не препятствует переносу.

| Что обнаружено | Следующий шаг |
|---|---|
| Не хватает `AGENTS.md` или командных документов | `harness-context`, `bootstrap-minimal` |
| Источник прототипа не определён | запросить точный путь; не подбирать источник самостоятельно |
| Нет `prototype-analysis.md` | `harness-source-analysis` |
| Нет `ds-precheck.md` | `harness-ds-precheck`; решение человека нужно только для П-находки или конфликта |
| Нет разрешённого плана A | `harness-prototype-plan`; проблемы имён, установки и импорта включить в ту же очередь |
| Есть незавершённая готовая задача A | выполнить её через `harness-work-session` |
| Не доказано сохранение поведения на текущих версиях | `harness-eval`, `skill_mode=prototype-parity` |
| Нет `team-patterns-production.md` | `harness-extract-prod` |
| План B/C отсутствует или устарел | `harness-production-plan` |
| Для подключения не хватает контракта или есть существенный конфликт | получить недостающие сведения либо подготовить проект решения; реализацию не брать в работу |
| Есть готовая задача B с завершёнными зависимостями | `harness-work-session` |
| Код B готов, но приложение целиком не проверено без сети | единственная задача `offline-runtime-lifecycle` через `harness-production-readiness`, `skill_mode=process` |
| Приложение проверено, но сборка не подтверждена | единственная применимая задача `runtime-bundle` |
| B завершён, остались внешние проверки и выпуск | продолжать готовые задачи C; отсутствие внешних данных не отменяет завершение B |
| Следующий шаг обращается к реальному стенду без разрешения | запросить разрешение именно на этот вызов; независимую работу не останавливать |
| Нет подтверждения выпуска | выполнить предусмотренные планом проверки C2 и передачу эксплуатации C3; получить итоговое решение владельца |

План B/C устарел, если изменились паспорт или техническая карта, отсутствуют
`plan_id`/`stage`/`phase`/`verification_level` либо у применимых проверок запуска
и сборки нет ровно одной ответственной задачи в плане. При конфликте фактов
покажи его и останови затронутую часть, не выбирая удобный статус.

Для проверки очереди, хешей и краткой передачи состояния используй
[служебные утилиты](references/artifact-tools.md), когда они действительно нужны.
Успех проверки JSON и статусы `done` не доказывают работоспособность приложения
или готовность выпуска. При автоматическом взятии задачи используй защищённую
цепочку из справочника; ошибку проверки нельзя обходить отдельным `claim_task`.

## Порядок работы

1. Кратко назови найденный этап и подтверждающие результаты. Перед анализом
   проверь версию прототипа, перед реализацией подключения — паспорт и
   `data-boundaries.md`, перед внешним вызовом — отдельное текущее разрешение.
2. Веди один профильный процесс и одну занятую задачу за раз. После результата
   обнови состояние и выбери следующий шаг до согласованного результата или
   реального препятствия. Подготовку контекста, анализ, предварительную проверку
   и разрешённый план можно сохранить одним подготовительным коммитом.
3. Выбирай готовую задачу по `depends_on` и текущим статусам Tasks MCP, затем
   по порядку фазы, приоритету и числовому ID. Передай `task_id`, определение,
   актуальные статусы и `verification_level` в `harness-work-session`.
   Не спрашивай выбор между равно допустимыми задачами; спроси только о
   взаимоисключающих вариантах архитектуры. Не повышай проверку до сборки
   всего сервиса по умолчанию.
4. Перед `prototype-parity` проверь все задачи A с тем же `plan_id`, включая
   добавленные позднее: они завершены, их `evidence.commit_sha` входят в
   проверяемый HEAD, а задач переноса с неопределённой принадлежностью к плану нет.
   Порядок записей и старый `depends_on` не заменяют эту проверку.
5. Ошибки текущего незавершённого результата исправляй внутри той же задачи.
   Независимые дефекты, изменения уже сданной работы и новые решения передавай
   планировщику. Сам по себе новый лог не требует новой задачи.
6. Если нужен человек, представь факты, варианты, последствия, рекомендуемый
   безопасный вариант и что он разблокирует. После решения сохрани его в
   предусмотренном документе и продолжай в разрешённом объёме.

Разрешённый безопасный локальный план покрывает перечисленные изменения
зависимостей, файлов фиксации версий, сборки и других защищённых путей.
Сохрани источник разрешения и точный перечень изменений. Не проси подтверждение
заново перед каждой задачей, веткой или коммитом. Если исходного разрешения нет,
достаточно одного подтверждения плана. Показать план до записи нужно в обоих
случаях, но при действующем разрешении это сообщение о ходе работы, а не остановка.

## Когда требуется отдельное решение

- Изменение поведения прототипа, П-находка или конфликт источников.
- Новое подключение либо существенный конфликт схемы, версии, авторизации
  или устройства процессов.
- Изменение зависимости или защищённого файла за пределами разрешённого плана.
- Внешний вызов, изменение общей БД, выполнение миграции, развёртывание либо
  другое существенное внешнее действие.
- Итоговое разрешение выпуска.

`НЕИЗВЕСТНО` не заменяй догадкой. Оно блокирует только зависимую работу.
Заполненный паспорт или статус `open` не являются разрешением внешнего действия.

## Независимые статусы B и C

После передачи результата B/C укажи:

| Поле | Что оно подтверждает |
|---|---|
| `Stage B code: COMPLETE / INCOMPLETE` | обязательная реализация закончена |
| `Stage B offline runtime: COMPLETE / NOT_GREEN / NOT_STARTED` | настоящий `create_app`/`app`, рабочая сборка зависимостей приложения и время жизни ресурсов проверены без сети для API и обработчика очереди |
| `Stage B bundle: COMPLETE / NOT_APPLICABLE / NOT_GREEN / NOT_STARTED` | актуальны чистая установка, сборка, состав пакета и проверки запуска собранных процессов |
| `Stage B overall: COMPLETE / INCOMPLETE` | код, запуск без сети и применимая сборка успешно проверены |
| `Stage C: NOT_STARTED / IN_PROGRESS / COMPLETE / DEFERRED / BLOCKED` | внешние реквизиты, изолированные проверки БД, стенд, эксплуатационные инструкции и решение о выпуске |
| `Release ready: YES / NO` | все обязательные проверки C пройдены и владелец разрешил выпуск |

Пустой `FastAPI()`, подменённая система зависимостей или только модульные тесты
не подтверждают запуск настоящего приложения. Команда должна действительно
выполнить нужные проверки, а не пропустить их каталог. Актуальность результатов
проверяй по `harness-pre-commit-check`, сохраняя исходную версию отчёта.

Проверку запуска без сети выполняет `harness-production-readiness:process`,
а не новый режим `harness-eval`. Режим `harness-eval:live` предназначен для
реальных отдельно разрешённых систем C. При отложенном C итог: «Этап B завершён;
этап C отложен; выпуск не разрешён». Не возвращай B в незавершённое состояние.

Для полного результата также нужны подтверждённое сохранение поведения,
точные версии контрактов и соответствие полей во всех подключениях, отсутствие
временного файлового обмена в рабочем пути либо решение сохранить его,
подтверждённые конечные состояния и внешние изменения, а также владельцы и
решения по оставшимся рискам. Один `make verify` этого не доказывает.

## Продолжение работы и делегирование

В режиме `/goal`, если он доступен в среде Кодового агента, ведущий продолжает
тот же маршрут по сохранённым результатам и статусам Tasks MCP. Отдельный
процесс управления или смена модели для этого не нужны.

Если среда предоставляет субагентов и делегирование разрешено, поручай им
только независимые части текущей задачи. Задачей в Tasks MCP, веткой,
коммитом и сдачей управляет один ведущий. Передавай исполнителю цель,
разрешённые файлы и критерии проверки, не допускай пересечения правок.
Используй текущие настройки модели; отдельный выбор моделей не входит в
этот маршрут. Результаты проверь перед объединением. Если субагентов нет,
выполняй работу последовательно — это не препятствие опромышливанию.

## Безопасность

Правила защиты описаны в `<harness_kit>/SAFETY.md`. Доступ к файлам ограничивает
владелец среды; комплект не меняет разрешения текущей сессии автоматически.
Настройки конкретных приложений в эту поставку не входят. Watcher использует
фильтр команд, а не песочницу ОС.
Не обходи отказ другим инструментом, исполнителем или повышением разрешений.

Не читай и не печатай `.env`, значения переменных окружения, ключи, пароли и
хранилища секретов. Используй имена и ссылки из кода и документов, проверки
наличия без значений либо проверку явно разрешённых несекретных полей.
`.env.example` доступен только если это разрешено действующими правилами.

Эталонный набор по внешнему стандарту не является обязательной частью переноса.
По отдельному запросу создавай его через `harness-golden`, а оценку агента на
выпущенном наборе — отдельной задачей `harness-eval`, `skill_mode=golden`.

## Результат

Кратко сообщи текущий этап, подтверждения, выполненный шаг и следующий шаг.
Если остановка действительно нужна — укажи точное недостающее решение, не
маскируй препятствие и не добавляй повторных подтверждений.
