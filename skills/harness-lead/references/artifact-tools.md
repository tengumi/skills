# Проверка плана и передача состояния

Используй при изменении очереди, фиксации выбранных входов или передаче
состояния. Не запускай все команды после каждой задачи: это служебные действия,
а не отдельный этап, новая задача или повод для подтверждения человека.

Программы находятся в `scripts/` установленного `harness-lead`.
Определи абсолютный путь к этому скиллу по расположению `SKILL.md`,
а не текущему рабочему каталогу. Обозначения команд ниже:

- `TOOL` — `<harness-lead>/scripts/harness_artifacts.py`;
- `CLAIM_TOOL` — `<harness-lead>/scripts/guarded_claim.py`;
- `KIT` — явно указанный путь `<harness_kit>` к корню `harness-kit-prom`;
- `SCHEMA` — `<harness_kit>/templates/tasks.schema.json`;
- `TARGET` — корень целевого репозитория.

Это обозначения явно заданных путей, не предложение искать значения в env.
Передавай пути в кавычках. Нужны Python 3.12 и POSIX-среда Linux/macOS.
Безопасная работа с путями без символических ссылок на Windows пока не реализована.
Для `validate-tasks` и `handoff` в среде утилит должны быть зависимости из
`<harness-lead>/scripts/requirements.txt`. `manifest` использует
стандартную библиотеку. Эти зависимости не добавляются в опромышливаемый сервис,
Tasks MCP или watcher. Не устанавливай их через запрещённый сетевой канал.

## Проверка очереди

```bash
python "$TOOL" validate-tasks --tasks "$TARGET/docs/harness/tasks.json" --schema "$SCHEMA"
```

Проверяются JSON Schema, уникальность ID во всех разделах, существование
зависимостей, отсутствие циклов, соответствие этапа и фазы, единственность
ответственных задач запуска и сборки. Ошибка содержит путь поля и код, а не
содержимое поля.

Для автоматической локальной последовательности «проверка → актуальные статусы →
взятие задачи» используй локальный `guarded_claim.py`:

```bash
python "$CLAIM_TOOL" --kit "$KIT" --repo "$TARGET" --task-id T-002 --state-dir "<каталог-состояния-Tasks-MCP>"
```

Схема и сервер берутся из указанного kit, проверяющая программа — из этого
скилла. Каталог состояния должен быть тем же, который использует подключённый
Tasks MCP для целевого репозитория, и находиться вне него. Поддерживается режим
`out_of_band`. Не создавай отдельную историю статусов случайным новым путём.
При ненулевом коде проверки нельзя обходить отказ отдельным `claim_task`.
После успеха повторно брать задачу не нужно. При потере ответа сначала получи
свежие статусы: операция уже могла выполниться. Утилита не сдаёт задачу,
не исполняет команды из плана и не заменяет проверку разрешений и смысла контракта.
Проверка статусов и взятие задачи не атомарны: за очередь отвечает один ведущий.

Для полного плана B, где применимы обе итоговые проверки, добавь:

```bash
--plan-id production-bc-<id> --require-runtime --require-bundle
```

Без этих флагов отсутствие ответственной задачи не считается доказанной ошибкой:
применимость определяет планировщик. Проверяй полную очередь, а не только новый
фрагмент. `valid: true` не доказывает качество разбиения задач, полноту контрактов,
разрешения, актуальность результатов или готовность выпуска. Ошибку генерации
исправь в рамках планирования без нового запроса к человеку.

## Снимок выбранных файлов

```bash
python "$TOOL" manifest --root "$TARGET" --file docs/harness/pre-industrialization-spec.md --file docs/harness/data-boundaries.md --file docs/harness/team-patterns-production.md --output "$TARGET/.tmp/harness/plan-inputs.json"
```

Повторяй `--file` для точных относительных путей. Без него выбираются только
файлы, отслеживаемые Git. Для прототипа без Git укажи файлы явно.
Нет рекурсивного чтения всего рабочего каталога и раскрытия окружения.
Запрещённые имена, кеши, сборки и символические ссылки исключаются до открытия.
Явно указанный запрещённый или отсутствующий файл приводит к ошибке, а не
частичному успеху. Не включай отчёт в список его собственных входов.

`content_sha256` — хеш отсортированной карты «относительный путь → SHA-256
содержимого». Время изменения файла в него не входит. Исполнитель отвечает за
полноту выбранных входов; хеш не доказывает сохранение поведения или отсутствие
всех секретов. В плане сохрани также роль источника и Git-версию. При повторном
использовании не переписывай исходный отчёт под новую версию.

## Краткая передача состояния

Сохрани свежий ответ `tasks-mcp.list_open_tasks(include_all=true)` в безопасный
JSON без значений окружения и сырых логов, затем выполни:

```bash
python "$TOOL" handoff --tasks "$TARGET/docs/harness/tasks.json" --schema "$SCHEMA" --lifecycle "$TARGET/.tmp/harness/tasks-export.json" --output "$TARGET/.tmp/harness/handoff.json" --markdown "$TARGET/.tmp/harness/handoff.md"
```

Сводка использует текущие статусы MCP, а не `open` в определениях задач.
Неполная или несовместимая выгрузка отклоняется. В отчёт попадают статусы,
зависимости и структурированные подтверждения; произвольные заметки, ошибки
и содержащиеся в них секреты не копируются.

Это снимок входных данных, не запрос к действующему серверу. Даже все `done`
не устанавливают завершение B/C или готовность выпуска. Ведущий отдельно
проверяет версии, результаты и разрешения. Утилита не занимает и не сдаёт
задачи, не меняет Git и не запускает тесты или сборку.

Результаты создаются только по указанным путям и по умолчанию не перезаписываются.
`--replace` предназначен для осознанного обновления собственного отчёта.
Нельзя перезаписывать входные определения, схему, статусы или выбранные исходники.
JSON и Markdown записываются атомарно по отдельности, не одной транзакцией.
Коды выхода: `0` — успех; `1` — неверная очередь; `2` — ошибка входа или доступа.
