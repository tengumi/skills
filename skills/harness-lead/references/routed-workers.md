# Модели исполнителей внутри `/goal`

Опциональный эксперимент для явно запрошенного выбора моделей субагентов.
Обычный последовательный маршрут не меняется. Это не новый этап, не отдельная
очередь и не обязательный preflight.

По умолчанию выбор локальный: без TypeSafe, Venice, ключей или отдельного API.
Решение вычисляется кодом по признакам задачи. Это не локальная LLM: сами
субагенты работают через обычный доступ кодового агента и расходуют его лимиты.

## Кто чем управляет

`/goal` хранит цель в ведущем чате. `harness-lead` выбирает одну готовую capability,
а `harness-work-session` владеет её единственным claim, веткой, проверкой и submit.
Внутри этой capability можно поручить независимые части отдельным исполнителям.
Они не вызывают Tasks MCP, не создают ветки, не коммитят, не меняют `/goal` и не
запускают своих исполнителей. Максимум три активных исполнителя; ограничение
текущего runtime может быть строже.

Модель ведущего не меняется. Для каждого исполнителя выбирается модель из
актуального каталога runtime, фиксированная на одну попытку. Явный выбор модели
пользователем важнее рекомендации роутера; не заменять её молча. Без разрешения
на выбор моделей использовать наследуемую модель и обычное делегирование.

## Узкий пакет задачи

Передать исполнителю цель, точные разрешённые файлы, необходимые исходники и
профильный skill, критерии готовности и команды проверки. Передавать только
нужный контекст, не полный журнал ведущего. Новый исполнитель запускается без
fork всей истории. Это сокращает его вход, но **не отключает накопление контекста
самого ведущего** и не реализует SKILL.state для всех модельных шагов.

Общий интерфейс/схему сначала согласовать в текущей capability. Не поручать
одновременные правки пересекающихся файлов; общий config, DI, manifest/lock,
генерацию клиентов и окончательное соединение компонентов оставить одному
ответственному. Зависимые части выполнять последовательно. Не дробить работу
на микрозадачи только ради субагентов и не добавлять их в Tasks MCP.

## Выполнение

Использовать [goal-workers](../../../tools/goal-workers/README.md) для подготовки
пакета и записи состояния, а [local-route](../../../tools/goal-workers/local-route.mjs)
— для решения по модели. Этот entrypoint принимает только `packet` и `catalog`,
отклоняет настройки внешнего провайдера и не требует runtime Jev.
Утилиты не запускают модель и не меняют lifecycle.

| Часть работы | Минимальный класс модели |
|---|---|
| Механический перенос, низкий риск и понятные требования | fast |
| Реализация или подключение по известному контракту | balanced |
| Архитектура, review, высокий риск или неопределённость | strong |

Классы — локальная политика, не измеренный рейтинг моделей. Ведущий выбирает
проверенные доступные model IDs, не придумывает их и не занижает риск ради
скорости. Если подходящего класса/ёмкости нет, не подменять его слабой моделью:
выполнить часть ведущим либо сообщить конкретное ограничение. Не требовать ключ
API роутера для продолжения.

1. После существующего claim выделить полезную независимую часть работы.
   Получить решение роутера, затем `prepare`: оно резервирует область и возвращает
   параметры native `spawn_agent`. Внешний классификатор не определяет разрешения.
2. Проверить модель/effort по доступным параметрам инструмента. Вызвать именно
   native subagent tool, не создание пользовательского чата и не запуск нового
   CLI с ослабленными разрешениями. Записать возвращённый worker id через
   `dispatch`. Если инструмента нет — продолжать последовательно, не придумывать
   скрытый runtime.
3. После результата записать `finish`. Статус `REVIEW_REQUIRED` означает только
   получение ответа. Ведущий проверяет diff/область и самостоятельно выполняет
   нужные проверки; затем записывает `review`. Самоотчёт исполнителя не evidence.
4. Перед submit общей задачи дождаться всех исполнителей и проверить соединение
   их изменений на исходном уровне verification. Несвязанные изменения не
   принимать. Новая модель не позволяет ослабить parity, runtime или bundle gate.

После прерывания проверить state и native worker status. `PREPARED` может означать,
что запуск состоялся до записи id; `RUNNING` не означает, что процесс ещё жив.
Не запускать копию и не освобождать область по таймеру. Сначала выяснить состояние
первого исполнителя. Новая попытка — только после остановки/завершения прежнего,
проверки оставшегося diff и явного решения ведущего; автоматических бесконечных
перезапусков или смены модели после любого падения теста нет.

## Jev и границы данных

`local` — прозрачная локальная политика, **не ответ Jev**. При запросе без
отдельного API не запускать Jev launcher и не запрашивать ключ; ошибки локального
выбора не разрешают внешнюю передачу. `jev` через отдельный
[task-route](../../../integrations/jev-router/README.md#выбор-модели-для-исполнителя) — явный opt-in
к закреплённому адаптеру TypeSafe; сейчас разрешены только синтетические задачи.
Классификатор получает ограниченный набор признаков задачи и каталог моделей,
не исходники, паспорт, историю или значения окружения. При ошибке классификатора
записывается `policy_fallback`, а не успешное решение Jev. Отсутствие ключа
не мешает обычному Harness или локальному режиму.

Границы файлов в пакете и журнал предотвращают случайные пересечения при
соблюдении протокола, но не являются песочницей ОС. Доступы и approvals остаются
за платформой. Не менять provider, глобальный config или разрешения ради роутинга.

## Что считать улучшением

Сравнивать одинаковый вход и одинаковые независимые проверки: последовательный
фиксированный исполнитель, параллельные фиксированные исполнители, параллельные
исполнители с роутером. Отдельно учитывать время ведущего/проверок/повторов,
фактическое использование моделей и токены, если runtime их возвращает. Число
выбранных лёгких моделей не является измерением стоимости. Малый учебный прогон
не доказывает ускорение всего A → B → C или надёжность многочасового `/goal`.
