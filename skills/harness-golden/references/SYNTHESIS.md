# Синтез и проверка golden-набора

## 1. Один профиль на запуск

В `run.json` сохрани задачу, режим, контракт, sources с ролями/locator/hash,
приоритет источников, эквивалентность, единицу оценки, target и бюджет. Форму
выхода агента получай из его контракта; не требуй заранее готового golden spec.
Фиксируй только решения, влияющие на результат. Простой кейс не требует отдельной
программы калибровки или математического решателя.

Нормативную часть профиля храни в `run.evaluation`: контракт, truth (содержание
или версии/hashes источников), приоритеты и эквивалентность. Изменение этих данных
делает старые проверки неактуальными. Контракт может разрешать любой JSON-ответ,
включая null; наличие ключа expected отличается от значения этого ключа.

Уточнение нужно при неизвестном правиле, которое меняет правильный ответ, а не
из-за отсутствия привычного файла. При проблеме одной группы продолжай остальные
независимые группы; явно укажи, какие случаи пока нельзя оценивать.

`business_review_draft`: один полный независимый вывод каждого ответа и одна
проверка естественности партии; второй свежий pass только по неоднозначным,
конфликтным, исправленным или существенно зависимым решениям.
`benchmark_release`: до генерации зафиксируй достаточную политику проверки:
для семантического oracle — два независимых вывода с разбором расхождений;
для полного executable oracle — controls, execution и проверка привязок.
Требуемую внешнюю приёмку не заменяй модельной. Draft можно повысить до release
на тех же входах, выполняя только недостающие проверки.

Нужны границы числа попыток и ремонтов; используй пользовательский бюджет.
Если его нет, назначь небольшой бюджет по масштабу задачи и сообщи его. Не
обещай, что любой target гарантированно достигается за заданное число попыток.
Различай реальную статистику потока и специально сбалансированный diagnostic
набор. Для квот заранее проверь совместимость целых counts и доступных сценариев.

## 2. Референсы и покрытие

Источники могут иметь роли reference, truth, contract и calibration, но роль
должна быть явной. Старый ответ агента не является truth без авторитетного
подтверждения. Показывай автору только разрешённые источники без secrets/PII.

Для корпуса строк, диалогов или документов сохрани стабильные reference IDs,
locator (например, file/sheet/row либо conversation ID) и версию источника.
Инвентаризируй переданные единицы; если прочитана только часть, укажи фактический
scope. Удаляй технический мусор и дубли, обезличивай нужные примеры. Неполные
диалоги исключай только если их нельзя использовать для разрешённого сценария
уточнения; отсутствие данных может быть намеренной осью оценки.

Сгруппируй пригодные примеры по осям текущей задачи, затем выбирай по целевому
покрытию, достаточности контекста и разнообразию. Фиксируй выбранные IDs и тип
преобразования для каждого case. Обычно достаточно 1–3 релевантных примеров;
это ориентир, не hard gate. Не изображай случайную выборку репрезентативной без
проверки распределения. Seed помогает повторить детерминированный отбор; для
модельной классификации сохраняй фактические решения и версии.

Короткие вопросы и структурные данные требуют естественного языка, schema,
полного контекста и разнообразия. Им не нужны document topology, appendix audit
или common-layer retention. Для свободных документов определи жанр, форму,
естественную длину и содержание частей. Общую шаблонную основу обрабатывай по
TEMPLATES.md. Разные семейства не объединяй в один усреднённый профиль.

## 3. Автор, финальный вход и независимый ответ

Автор может совмещать планирование и генерацию: ему нужны правила задачи,
референсы, сценарий и ограничения. Нет необходимости скрывать от автора
нормативные требования. При квотах держи планируемые классы отдельно от входа.
Не показывай автору ответы проверяемого агента для независимого holdout.

До языковой реализации кратко определи ситуацию, цель и существенное условие
сценария; затем напиши естественный вход по референсам. Это часть авторинга,
не отдельный обязательный агент или файл. Варьируй задачи, не только формулировки.

Начни с небольшой партии, покрывающей существенные типы входов. Для простой
детерминированной сборки достаточно smoke-control. После успешной проверки
расширяй партиями, размер которых соответствует длине входов и риску. Не
создавай отдельный agent/context на каждый короткий case без причины.

Изменения должны быть правдоподобными: одно отклонение может влиять на несколько
критериев. Не превращай документ в перечень намёков на проверку. Длину используй
как допустимый диапазон, а не цель для padding. История и runtime, необходимые
для ответа, должны присутствовать во входе.

До дорогого oracle проверь schema входа, дубли, приватность, ссылки и применимые
требования формы. Затем заморозь вход и его hash. Механический дефект оформления
можно исправить в пределах бюджета; содержательный ремонт создаёт revision.

Передай независимому verifier только финальные входы, их hash, truth и contract.
Используй свежий контекст без истории автора и других проверяющих; зафиксируй
фактический worker ID и переданные источники. Он не должен читать cases.jsonl с
готовыми gold или audit.jsonl с планом. Передавай очищенные данные прямо в вызове
либо через временный input-only файл. Если независимость недоступна, пометь
результат self_checked/provisional, не выдавай его за blind или release-grade.

Проверяющий проходит все применимые единицы. Для семантического ответа сохраняй
достаточные точные цитаты/локаторы; для отсутствия — scope поиска; для вычислений
— входные числа, операцию и результат. Не навязывай цитаты числовому oracle,
когда trace вычисления является достаточным доказательством.

Проверяй returned schema и hashes немедленно. Только структурный/транспортный
дефект допускает точечное исправление формы без изменения решения. Нельзя
дописывать недостающее смысловое evidence ради сохранения прежнего вывода:
в таком случае нужен новый независимый вывод затронутого решения.

Содержательное расхождение разрешай по источникам, а не голосованием. При узком
ремонте перепроверь изменённые единицы и возможные побочные эффекты; сохрани
действительные результаты остального. При неизвестных границах влияния сделай
полную перепроверку case. Сравнивай planned и derived только после этого.

Для каждого заявленного типа ошибки проверь различимость: какой конкретный
неверный ответ или действие должен быть отклонён на этом входе, и почему его
результат отличается от правильного. Проверь также допустимую альтернативу,
если она есть. При доступном evaluator исполни эти controls; иначе сохрани
обоснование и пометь проверку как неисполненную. Делай это по типам проверок
в существующем audit, без нового модельного pass на каждый case. Недоказанное
покрытие не засчитывай, но валидный case может остаться в наборе для иной цели.

Для агента действий gold задаёт результат, сохраняемые части состояния и
существенные запреты побочных действий. Проверяй trace, когда конечное состояние
может скрыть нарушение. Другой порядок независимых действий разрешён, если
контракт не требует обратного; не навязывай одну reference-траекторию.

## 4. Принятие и остановка

Case с доказанным неожиданным ответом может быть валидным, но не помогать квоте.
Не отправляй его в quarantine только из-за отличия от плана. Для итоговой
подборки сначала используй ready pool. Если target недостижим в бюджете, покажи
фактический результат и минимально необходимое изменение, не запускай бесконечные
замены. Сам target не даёт разрешения изменить правила правильности.

Hard failure: неразрешённая неоднозначность gold, утечка, недостаточное
обоснование, неверная привязка или обязательный нарушенный контракт. Метрики
естественности и сходства обычно диагностические; hard threshold допустим только
по явному контракту или проверенным controls, а не потому, что его придумал агент.
Одинаковая повторная причина в нескольких cases требует исправления процесса,
а не дальнейшего тиражирования. Не затрагивай уже подтверждённые независимые группы.

Перед quarantine укажи конкретный дефект, evidence и основание обязательности
проверки. Расхождение passes сначала разбери по источникам; само по себе оно
не доказывает дефект case. Не завершённая проверка или недоступный инструмент —
pending, не ready и не доказанный брак входа. Непопадание в квоту, слабое покрытие
отдельной ошибки и advisory-замечания не являются основаниями quarantine.
Реальную утечку, неразрешённую неоднозначность и нарушение обязательного контракта
не понижай до предупреждения; исправляй в бюджете, иначе исключай case. Эти
уточнения не меняют задним числом frozen rules существующих runs.

Измеряй хотя бы: requested/generated/ready/selected, причины исключений, число
ремонтов, фактическую долю классов, число verifier passes и файлов. Указывай время
только по измерению, а оценки и неизвестные значения обозначай явно.

## 5. Компактный пакет

Для нового run укажи `run.package_layout: "compact-v2"`. В корне итогового
каталога оставь ровно три служебных файла и одну папку `results/`:

1. `run.json` — профиль, контракт, источники, reference index/selection, бюджет,
   версии, counts, verification policy, явный `selected_case_ids` и список файлов.
   Итог храни здесь же в `summary`: непустой текст `outcome` и список `limitations`.
2. `cases.jsonl` — одна запись на case: `case_id`, `input`, `expected`,
   `input_sha256`, `status`, `reference_ids` и достаточные evidence/метаданные.
3. `audit.jsonl` — записи о controls, назначениях, реальных независимых passes,
   ремонтах и исключениях. Private; не передавать verifier целиком.

`results/` — только выбранные финальные cases и ответы в удобном человеку виде.
Обычно для табличных задач достаточно одного `benchmark.xlsx`; для документов —
финальных входных документов и одной таблицы с ID, ссылками и ответами. Выбери
один основной формат по задаче/запросу, не дублируй его в HTML, CSV и Markdown без
необходимости. Покажи ID, вход/контекст, эталон и нужные оси оценки; технические
hashes, worker IDs, логи и планы в человеческую выдачу не включай. Язык — язык
пользователя. Краткий статус draft/release и ограничения помести в сам бенчмарк,
без отдельного README или report.md. При отсутствии выбранных cases оставь
`results/` пустой и объясни итог в `run.summary`, не имитируй готовый бенчмарк.

Каждый файл `results/` объяви в `run.files`: относительный `path`, `sha256` и
`case_ids` — уникальные ID представленных выбранных случаев (для общих материалов
пустой список). Вместе файлы должны охватывать все `selected_case_ids`.
`run.results_entrypoint` указывает на основной файл, с которого
человек начинает работу; при пустой выдаче поле отсутствует или равно null.
Вложенные папки допустимы для входных документов и действительно нужных ресурсов;
все ссылки должны работать внутри переносимого пакета, без symlinks и temp paths.
Сверь ID, состав, входы и ответы экспорта с `selected_case_ids` и `cases.jsonl`:
никаких pending/quarantine, устаревших revisions или заново придуманных gold.
Папка для человека может содержать ответы; тестируемому агенту передавай только
входы и разрешённый контекст, не всю папку/книгу с эталонами.

`input_sha256` — SHA-256 UTF-8 JSON поля input с `sort_keys=True`,
`ensure_ascii=False`, `separators=(',', ':')`. Финальные external fixtures,
если они нужны, сохраняй в `results/` и перечисляй в `run.files`;
hash входного объекта не заменяет проверку содержимого внешнего документа.
Для case status используй `ready`, `quarantined` или `pending`; уровень
проверенности всего набора храни в run, не смешивай его с доменным вердиктом.

Записи audit имеют `type` и фактические данные события. Verification record
содержит `type: verification`, `case_id`, `input_sha256`, `evaluation_sha256`,
`expected_sha256`, `method`
(`fresh_context`, `deterministic` или `self_check`), `worker_id`/tool version,
`result`, `evidence` и scope. Такой record фиксирует проведённую проверку;
само наличие записи не доказывает независимость или правильность её содержания.
`evaluation_sha256` хеширует `run.evaluation`, `expected_sha256` — фактически
выведенный ответ; для обоих используй ту же канонизацию JSON, что для input.
После ремонта помечай прежние записи `superseded: true`; они сохраняют историю,
но не подтверждают новую revision. Никогда не перепривязывай изменённый gold или
новые правила к старому pass без требуемой проверки.

Не копируй исходники в каждый run: достаточно locator/hash, если источник будет
доступен для повторной проверки. Временные input-only выгрузки, промежуточные
passes, сборочные скрипты и диагностику держи вне итогового каталога. Сохрани
существенные результаты, evidence и историю revisions в cases/audit до удаления
своих временных файлов. Неотобранные cases остаются в служебных данных, не в
`results/`; их нужное для проверки содержимое не теряй за временными путями.
В release сохраняй более полное evidence в том же журнале, не добавляя папки.
Старые runs и исходные пользовательские файлы не очищай и не мигрируй без запроса.
Runs без `package_layout` валидируются в прежнем формате с `report.md`.

Проверь пакет командой `python scripts/validate_run.py RUN_DIR` из папки skill.
Это структурная проверка, не oracle. Если runtime/формат другой, выполни те же
проверки доступными средствами; не устанавливай новую инфраструктуру без нужды.
Ошибка упаковки требует исправить упаковку, а не отправлять валидные cases в
quarantine. Вывод validator сохраняй записью audit, не отдельным отчётом.
Готовые passes переиспользуй только при неизменных input, truth и contract hashes.
Завершай после выполнения согласованного режима; не добавляй новые круги аудита
после уже успешной проверки без конкретной причины.
