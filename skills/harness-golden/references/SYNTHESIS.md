# Генерация и проверка эталонного набора

## 1. Профиль запуска

В `run.json` сохрани задачу, режим, контракт, источники с ролями/адресами/хешами,
их приоритет, правило эквивалентности, единицу оценки, целевой объём и бюджет.
Форму ответа получай из контракта агента. Не требуй заранее готовой спецификации
и фиксируй только влияющие на результат решения. Простой случай не требует
отдельной программы калибровки или математического решателя.

Нормативные данные хранятся в `run.evaluation`: контракт, источники правильности
(содержание либо версии/хеши), приоритеты и эквивалентность. Изменение этих
данных делает прежние проверки неактуальными. Контракт может разрешать любой
JSON-ответ, включая `null`; наличие ключа `expected` не равно его значению.

Уточняй неизвестное правило, меняющее правильный ответ, а не отсутствие
привычного файла. Продолжай независимые группы и явно отмечай случаи, которые
пока невозможно оценить.

| Режим | Достаточная проверка |
|---|---|
| `business_review_draft` | Один полный независимый вывод каждого ответа и проверка естественности партии. Второй свежий разбор — для неоднозначных, конфликтных, исправленных или существенно зависимых решений |
| `benchmark_release` | Политику зафиксировать до генерации. Для смысловых ответов — два независимых вывода и разбор расхождений. Для полного исполнимого правила — контрольные примеры, фактическое выполнение и проверка привязок |

Требуемую внешнюю приёмку не заменяй модельной. Черновой набор можно повысить
до выпущенного на тех же входах, выполняя только недостающие проверки.

Используй бюджет пользователя на попытки и исправления. Если он не указан,
назначь небольшой соразмерный бюджет и сообщи его. Не обещай достижение любого
объёма за фиксированное число попыток. Различай естественное распределение
реального потока и специально сбалансированный диагностический набор.
Для квот заранее проверь совместимость целых количеств и доступных сценариев.

## 2. Примеры и покрытие

Явно разделяй роли источников: `reference` — форма/контекст, `truth` —
правильность, `contract` — требования к агенту, `calibration` — контрольные
примеры для проверки метода. Старый ответ агента не является источником
правильности без авторитетного подтверждения. Передавай автору только
разрешённые и при необходимости обезличенные материалы.

Для строк, диалогов и документов сохрани стабильные ID примеров, адрес
(файл/лист/строка либо ID диалога) и версию. Учти все переданные единицы;
если прочитана часть, укажи фактический объём. Удали технический мусор и дубли,
обезличь примеры. Неполный диалог исключай только если его нельзя использовать
для допустимого сценария уточнения: отсутствие сведений может быть осью оценки.

Сгруппируй пригодные примеры по осям задачи. Выбирай по нужному покрытию,
достаточности контекста и разнообразию. Для каждого случая сохраняй ID
применённых источников и тип преобразования. Обычно достаточно 1–3 относящихся
примеров, но это ориентир. Случайная выборка не доказывает представительность
без проверки распределения. Начальное число генератора помогает воспроизвести
детерминированный отбор; модельные решения сохраняй вместе с версиями.

Коротким вопросам и структурным данным нужны естественный язык, схема,
полный контекст и разнообразие, а не проверка структуры длинного документа.
Для свободных документов определи жанр, форму, естественную длину и содержание
частей. Подтверждённую общую основу обрабатывай по
[TEMPLATES.md](TEMPLATES.md). Не усредняй разные семейства одним профилем.

## 3. Автор и независимый ответ

Автор может совмещать планирование и генерацию; ему нужны правила, примеры,
сценарий и ограничения. Скрывать нормативные требования не нужно.
Планируемые классы держи отдельно от входа. Для независимого контрольного набора
не показывай автору ответы проверяемого агента.

Перед текстом кратко определи ситуацию, цель и существенное условие, затем
создай естественный вход. Это часть генерации, не обязательный отдельный
исполнитель или файл. Варьируй задачи, а не только формулировки.

Начни с небольшой партии существенных типов входов. Для простой
детерминированной сборки достаточно короткого контрольного примера. После
успеха расширяй партиями по длине входов и риску; не создавай отдельного
исполнителя на каждый короткий случай без причины.

Изменения должны быть правдоподобными. Одно отклонение может затронуть несколько
критериев, но документ не должен стать списком подсказок к проверке.
Длина — допустимый диапазон, а не повод добавлять пустой текст. История и
состояние среды, необходимые для ответа, должны присутствовать во входе.

До дорогого определения ответа проверь схему входа, дубли, приватность,
ссылки и требования формы. Зафиксируй финальный вход и его хеш.
Механическое исправление оформления допустимо в бюджете; изменение содержания
создаёт новую версию.

Независимому проверяющему передай только финальные входы, их хеши, контракт
и источники правильности. Используй свежий контекст без истории автора и
чужих решений. Сохрани фактический ID исполнителя и переданные источники.
Он не должен читать `cases.jsonl` с готовыми эталонами или весь `audit.jsonl`.
Передай очищенные данные прямо либо временным файлом только со входами.
Если независимая проверка недоступна, обозначь результат
`self_checked/provisional`, не выдавай его за независимый или готовый к выпуску.

Проверяющий охватывает все применимые единицы. Для смыслового ответа нужны
достаточные точные цитаты/адреса; для вывода об отсутствии — область поиска;
для вычисления — входные числа, операция и результат. Не требуй цитат там,
где расчёт полностью подтверждает ответ.

Сразу проверь схему и хеши полученного результата. Исправление только формы
допустимо при технической ошибке без изменения решения. Недостающее смысловое
доказательство нельзя дописать ради сохранения прежнего ответа: нужен новый
независимый вывод затронутого решения.

Разрешай содержательные расхождения по источникам, не голосованием.
После узкой правки проверь изменённые единицы и возможные побочные эффекты,
сохрани действительные остальные результаты. Если граница влияния неизвестна,
перепроверь случай полностью. Планируемый класс сравнивай с выведенным только
после проверки.

Для каждого заявленного типа ошибки опиши конкретный неверный ответ или
действие, которое должно быть отвергнуто, и отличие от правильного.
Проверь допустимую альтернативу, если она есть. При доступном инструменте
оценки выполни контрольные примеры; иначе сохрани обоснование и отметь,
что проверка не исполнялась. Достаточно записей по типам проверок в существующем
журнале, без новой модельной проверки каждого случая. Недоказанное покрытие
не засчитывай; сам корректный случай может оставаться полезным для другой цели.

Для агента действий эталон задаёт конечный результат, сохраняемые части
состояния и существенные запреты. Проверяй последовательность действий,
когда конечное состояние может скрыть нарушение. Другой порядок независимых
действий допустим, если контракт не требует обратного; не навязывай единственную
образцовую последовательность.

## 4. Принятие и остановка

Неожиданный, но доказанный ответ может быть корректным и лишь не подходить
к квоте. Это не причина исключать случай как дефектный. Для итоговой подборки
сначала используй уже проверенные случаи. Если цель недостижима в бюджете,
покажи результат и минимально нужное изменение; не запускай бесконечные замены.
Целевой объём не разрешает менять правила правильности.

Обязательные причины отказа: неразрешённая неоднозначность эталона, утечка,
недостаточное доказательство, неверная привязка или нарушение обязательного
контракта. Естественность и сходство обычно диагностические; жёсткий порог
допустим по контракту или проверенным контрольным примерам, не по догадке агента.
Одинаковая ошибка в нескольких случаях требует исправить способ генерации,
не затрагивая уже подтверждённые независимые группы.

Перед `quarantined` укажи конкретный дефект, доказательство и обязательность
проверки. Разногласие проверяющих само по себе не доказывает брак.
Незавершённая проверка или недоступный инструмент — `pending`, а не `ready`
и не доказанный дефект входа. Непопадание в квоту, слабое покрытие одной ошибки
и необязательное замечание не являются основанием `quarantined`.
Утечку, неоднозначность и нарушение обязательного контракта не понижай
до предупреждения: исправь в бюджете, иначе исключи случай. Не меняй
закреплённые правила существующего запуска задним числом.

Покажи как минимум запрошенное, созданное, готовое и выбранное количество,
причины исключений, число исправлений и независимых проверок, фактические
доли классов и число файлов. Время — только измеренное; оценки и неизвестные
значения обозначай явно.

## 5. Компактный пакет `compact-v2`

Для нового запуска задай `run.package_layout: "compact-v2"`.
В корне итогового каталога ровно три служебных файла и папка `results/`:

1. `run.json`: профиль, контракт, источники, перечень и выбор примеров, бюджет,
   версии, количества, политика проверки, явный `selected_case_ids`, перечень
   файлов. В `summary` — непустой `outcome` и список `limitations`.
2. `cases.jsonl`: одна запись на случай — `case_id`, `input`, `expected`,
   `input_sha256`, `status`, `reference_ids` и достаточные доказательства/
   метаданные.
3. `audit.jsonl`: контрольные примеры, назначения, реальные независимые
   проверки, исправления и исключения. Журнал закрыт от проверяющего целиком.

`results/` содержит только выбранные финальные случаи и ответы для человека.
Для таблиц обычно достаточно `benchmark.xlsx`, для документов — финальных
входных файлов и одной таблицы с ID/ссылками/ответами. Выбери основной формат
по запросу, не дублируй без нужды в HTML, CSV и Markdown. Покажи ID, вход,
контекст, эталон и нужные оси оценки. Хеши, ID исполнителей и логи оставь
в служебных файлах. Язык выдачи — язык пользователя.

Статус черновика/выпуска и ограничения помести в сам итоговый набор, без
отдельного README или report.md. Если ничего не выбрано, оставь `results/`
пустой, объясни итог в `run.summary`, не имитируй готовый результат.

Каждый файл `results/` объяви в `run.files`: относительный `path`, `sha256`,
уникальные `case_ids` представленных выбранных случаев. Для общего материала
список пуст. Все файлы вместе охватывают `selected_case_ids`.
`run.results_entrypoint` указывает на основной файл; при пустой выдаче
отсутствует либо равен `null`. Вложенные папки нужны только для входных
документов/ресурсов. Ссылки работают внутри переносимого пакета, без временных
путей и символических ссылок.

Сверь ID, состав, входы и ответы выдачи с `selected_case_ids` и `cases.jsonl`:
никаких `pending`/`quarantined`, старых версий или заново придуманных ответов.
Проверяемому агенту передавай только входы и разрешённый контекст, не всю
человеческую выдачу с эталонами.

`input_sha256` — SHA-256 UTF-8 JSON поля `input` с `sort_keys=True`,
`ensure_ascii=False`, `separators=(',', ':')`. Финальные внешние входные файлы
храни в `results/` и перечисляй в `run.files`: хеш объекта `input` не заменяет
проверку содержимого документа. Статус случая — `ready`, `quarantined` или
`pending`; проверенность всего набора хранится в `run` и не смешивается
с предметным решением.

Запись проведённой проверки содержит:

```text
type: verification
case_id
input_sha256
evaluation_sha256
expected_sha256
method: fresh_context | deterministic | self_check
worker_id / версия инструмента
result
evidence
scope
```

Запись фиксирует событие, но сама не доказывает независимость и правильность.
`evaluation_sha256` хеширует `run.evaluation`, `expected_sha256` — фактически
выведенный ответ; канонизация JSON та же, что для входа. После исправления
помечай старые записи `superseded: true`: они сохраняют историю, но не
подтверждают новую версию. Не привязывай изменённый ответ или новые правила
к старой проверке.

Не копируй исходники в каждый запуск: адреса/хеша достаточно, если источник
будет доступен для повторной проверки. Временные выгрузки только со входами,
промежуточные ответы, сборочные скрипты и диагностику держи вне итогового
каталога. Комментарии в своих скриптах пиши по-русски.
До удаления собственных временных файлов сохрани существенные результаты,
доказательства и историю версий в служебных данных. Неотобранные случаи
остаются там, не в `results/`; нужное для проверки содержимое не теряй
за временным путём. Для выпуска сохраняй более подробные доказательства
в том же журнале, не плодя папки. Старые запуски и файлы пользователя
не очищай и не мигрируй без запроса. Запуски без `package_layout` проверяются
в прежнем формате с `report.md`.

## 6. Итоговая проверка

Программа находится в `scripts/` установленного скилла `harness-golden`.
Подставь абсолютный путь к этому скиллу, не к текущему рабочему каталогу:

```bash
python "<harness-golden>/scripts/validate_run.py" "<каталог-набора>"
```

Это проверка структуры, не источник правильного ответа. Если среда или формат
не позволяют её выполнить, проведи те же проверки доступными средствами
и честно укажи способ; не добавляй инфраструктуру без нужды.
Ошибку упаковки исправляй в упаковке, не исключая корректные случаи.
Результат программы запиши в журнал, не отдельным отчётом.
Проведённые проверки действуют только при неизменных хешах входа,
источников правильности и контракта. Заверши после согласованного режима;
не добавляй новые круги аудита после успеха без конкретной причины.
