# Проверка прототипа по правилам команды

Выполни на шаге A1 сразу после
[harness-source-analysis](../harness-source-analysis/SKILL.md).
Входы: исходный прототип, `prototype-analysis.md` и командный
`docs/harness/mle-pep8.md`. Выход: `docs/harness/ds-precheck.md` в целевом
репозитории. Исходный код и правила команды не меняй.

## Как классифицировать

Для каждого правила спроси: изменится ли хотя бы на одном классе входов
результат, исключение, конечное состояние, число повторов или внешнее действие?

| Класс | Смысл | Что делать |
|---|---|---|
| Ф — форма | Меняется устройство кода, наблюдаемое поведение остаётся тем же | Добавить требование к задаче переноса соответствующего функционального блока |
| П — поведение | Меняется хотя бы один наблюдаемый результат или путь ошибки | Получить решение: сохранить как есть или отдельно изменить после фиксации исходного поведения |
| О — оптимизация | Меняется только скорость, память или необязательное оформление | Записать в список отложенных улучшений, не блокировать перенос |
| `OK` | Правило соблюдено | Зафиксировать |
| `N/A` | Правило неприменимо | Указать причину |

При сомнении между Ф и П выбирай П. Успешный основной сценарий не доказывает
сохранение обработки ошибок: сравни исключения, завершение, повторы и действия.

## Особо чувствительные правила

| Правило | На что смотреть |
|---|---|
| 1.1 Python 3.12+ | Соответствие командной среде; несовместимости фиксируются, не маскируются |
| 1.2 Аннотации DataFrame | Форма или `N/A`, если DataFrame нет |
| 1.3 Имена колонок | Внутреннее переименование может быть формой; изменение ключей результата — поведение |
| 1.4 `.pickle` → `.json` | Изменение формата, который читают или сравнивают, — поведение |
| 1.5 Равенство длины входа/выхода | Исправление скрытой потери элементов — изменение поведения |
| 1.6 Промпт в `.md` | Форма только при побайтовом сохранении текста и SHA-256 |
| 1.7 Обработка исключений | Смотри отдельное правило ниже |
| 1.8 Очистка символов промпта | Изменяет промпт и хеш: класс П |
| 1.9 Параметры в типизированных настройках | Форма только при точных прежних значениях и правилах загрузки; `None` нельзя заменить на `False` |
| 1.10 Передача зависимостей снаружи | Форма лишь при сохранении времени жизни, состояния и поведения |
| 1.11 Сужение вариантов типов | Часто меняет допустимые входы: класс П |
| 1.12 Неиспользуемый код | Только кандидат для проверки использования; не удалять |
| 1.13 Чтение/запись вне логики | Разделение можно выполнить как форму; замена файлов API/БД относится к этапу B |
| 2.1 Версии зависимостей | Требование к процессу; точная версия иногда влияет на результат |
| 2.2 Ноутбуки | Уточняет состав источника для анализа |
| 3.1 Тестовые примеры | Требование к проверке и передаче по действующей версии документа команды |
| 4.1 `set`/`dict` для поиска | Обычно оптимизация |
| 4.2 Векторизация | Обычно оптимизация |
| 4.3 Файловые операции в `predict` | Форма и/или оптимизация при сохранении поведения |
| 4.4 Кеширование лемматизации | Оптимизация только если операция не зависит от скрытого состояния |
| 4.5 `torch.no_grad()` | Обычно оптимизация, но проверь применимость к реальному процессу |
| 4.6 Накопление коллекций | Обычно оптимизация |

Таблица — ориентир, не замена чтения кода. Проверь все правила актуального
командного документа, включая отсутствующие в таблице, и не выдумывай его версию.

### Исключения и пустые результаты

Различай по коду, а не по названию:

- Ошибка, замаскированная под `[]` или другой успешный ответ: кандидат на
  отдельное изменение поведения. Не заменяй автоматически исключением
  и не предполагай, что очередь затем повторит задачу.
- Штатный результат «ничего не найдено»: сохранить.
- Широкий `except Exception` или перехват `AttributeError`: сужение допустимо
  как форма только при доказанном сохранении всего затронутого поведения,
  включая ошибочные входы. Совпадения успешного пути недостаточно.

### Файлы и неиспользуемый код

Отделение файловых операций показывает места будущих промышленных подключений,
но не определяет их устройство. Не выводи из файла предполагаемый API,
инструмент MCP, очередь, таблицу или хранилище.

Предполагаемый неиспользуемый код передай на двухэтапную проверку использования
и решение владельца. Пустой слой, заданный командным шаблоном, не является
мусором. В этом скилле не удаляется ничего.

## Содержание `ds-precheck.md`

1. Имя и снимок прототипа, факт чтения анализа, версия правил команды.
2. Сводка количества `OK`, `N/A`, Ф, П, О.
3. Таблица П: ID, правило, файл/строка, наблюдение, почему меняется поведение,
   затрагивается ли контракт (`contract-touch`).
4. Таблица Ф: правило, источник, требуемая структурная правка, функциональный
   блок, который отвечает за неё, и условия сохранения поведения.
5. Список отложенных улучшений О с причиной отсрочки и состоянием `deferred`.
6. Будущие подключения, которые потребуются на этапе B; допускается явно
   пустой раздел.
7. Все соблюдённые и неприменимые правила, чтобы было видно полное покрытие.

Для каждой П-находки предложи два решения:

- сохранить поведение и отметить известное отклонение от MLE PEP8;
- отдельно изменить поведение после фиксации и успешной проверки исходного
  результата; потребуются тесты ошибочных сценариев, `intentional_deviations`
  и источник новых ожидаемых ответов.

Решение человека, его область, дата и источник фиксируются явно.
Нельзя менять ожидаемый результат внутри переноса, чтобы скрыть расхождение.

## Как продолжать

Ф-находки входят в критерии существующих функциональных задач
[harness-prototype-plan](../harness-prototype-plan/SKILL.md); отдельная задача
на каждый пункт не нужна. О остаются отложенными до успешной проверки переноса
и последующего отдельного решения. П блокирует только затронутый блок,
если решение ещё не принято; независимая работа продолжается.

Проверь, что все правила получили статус, каждая П-находка содержит два
варианта, а прототип не изменён относительно исходного состояния.
Если П и конфликтов нет, сразу верни управление
[harness-lead](../harness-lead/SKILL.md) без нового подтверждения.
