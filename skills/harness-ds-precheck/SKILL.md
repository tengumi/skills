# harness-ds-precheck — триаж прототипа против MLE PEP8

## Что делает и чего не делает

Скилл сверяет прототип со стандартом MLE PEP8 ДО переноса и раскладывает
нарушения по трём маршрутам, чтобы все они были известны на старте, а не
обнаруживались по одному в ходе доводки.

Скилл НЕ улучшает и НЕ правит код. Опромышливание ≠ улучшение. Только
диагностика и сортировка; правки применяются позже — план переноса (класс Ф),
решение человека (класс П) или бэклог (класс О).

## Когда и на чём

- Шаг **A1**, сразу после `harness-source-analysis`.
- Вход: код **прототипа** (source), `prototype-analysis.md` (что реально есть),
  `docs/harness/mle-pep8.md` (правила, READ-ONLY).
- Выход: `ds-precheck.md` рядом с `prototype-analysis.md`.
- При наличии класса П или реального конфликта человек принимает решение после
  A1, ДО плана (A3). Если их нет и запуск orchestrated, сразу вернуть управление
  `harness-productionize` для планирования без отдельного checkpoint.

## Метод: один вопрос на каждое правило

По каждому правилу 1.1–4.6 определи статус прототипа и, если правило нарушено,
**класс находки**. Класс назначается ровно одним вопросом:

> Если применить это правило, изменится ли наблюдаемое поведение хотя бы на
> одном классе входов: output, exception/terminal state, retries или side effect?

- **Нет, поведение то же** → класс **Ф (форма)**. Чинится при переносе, контракт
  остаётся зелёным. Находка становится acceptance-пунктом уже существующего
  capability-slice; отдельную задачу на одну Ф-находку не создавать.
- **Да, поведение меняется** → класс **П (поведение)**. Это уже не
  опромышливание. НЕ применять внутри port/layout/hardening задачи. Вынести на
  решение человека; при «изменить» создать отдельную approved behavior-change
  задачу с тестом failure semantics, `intentional_deviations` и provenance
  golden. Исходный oracle сначала должен быть зафиксирован и зелён.
- **Не влияет на выход, только скорость/память/стиль** → класс **О
  (оптимизация)**. Записывается в cleanup/optimization ledger этого документа,
  не превращается в задачу этапа A и не блокирует перенос.

Плюс два не-нарушения: **OK** (прототип уже соответствует) и **N/A** (правило не
применимо — например, нет pandas/torch).

При сомнении между Ф и П — ставь **П**. Осторожнее = безопаснее: лучше человек
подтвердит безобидную форму, чем мы молча сменим поведение.

## Ловушки контракта — форма, которая на самом деле поведение

Это самая важная часть. Несколько правил **выглядят** как форма, но трогают
`prototype-contract.json` (SHA256 промптов, поля схем, дефолты) или выходной JSON.
Для них Ф действительна ТОЛЬКО при дополнительном условии, иначе это П:

- **1.6 (промпт → .md)** — Ф только при **байт-в-байт** переносе текста промпта.
  Любое переформатирование/чистка при выносе меняет SHA256 → **П**.
- **1.8 (лишние символы в промте)** — почти всегда **П**: чистка промпта меняет
  SHA256. Это осознанное отклонение, не «причёсывание формы».
- **1.9 (параметры → pydantic-конфиг)** — Ф только если дефолты сохранены
  **точь-в-точь**. Типичная ошибка: дефолт `None` молча превращается в `False`.
  Изменился дефолт → изменилось поведение → П.
- **1.3 (английские имена колонок)** — Ф если имена внутренние; **П** если имена
  попадают в выходной JSON/схему (переименование меняет ключи на выходе).
- **1.4 (.pickle → .json)** — **П**, если артефакт кто-то читает или с ним
  сравнивается: формат сериализации — часть наблюдаемого поведения.
- **1.11 (вариативность типов)** — обычно **П**: удаление ветки типа/Optional
  меняет поведение для входов, что шли по убранной ветке.

Если правило-ловушка сработало — заводи находку класса П с пометкой
`contract-touch` и предложи человеку два варианта (см. формат ниже).

### Особые маршруты

- **1.7 — таксономия error-handling A/B/C.** Различать ПО КОДУ, не по слову
  «fallback»: **A** — маскирующий error-fallback (`except: return []`,
  проглатывает сбой) → кандидат на fail-fast, но точные exception/terminal/retry
  semantics задаёт отдельная approved задача; нельзя автоматически предполагать,
  что очередь ретраит (П); **B** —
  штатная пустая ветка (валидный «ничего не найдено») → сохранить; **C** —
  широкий `except Exception`/ловля `AttributeError` → сузить до конкретных
  исключений (часто Ф, если поведение на успешном пути то же).
- **1.13 — отметь явно как «что это открывает».** Если прототип читает/пишет
  данные прямо в логике, разделение IO готовит будущую замену файлов на
  утверждённую boundary: API/tool/queue/DB/storage. Механизм не выводится из
  прототипа. Это НЕ делается в переносе (новая фича = эпик после заморозки),
  но всплыть должно здесь, чтобы потребность в персистентности была видна на
  старте, а не обнаружилась поздно.
- **1.12 — никогда не предлагай удаление как факт.** Только сигнал в двухтактный
  аудит. Пустой каркас-слой, заданный шаблоном команды (например, слой
  репозиториев/моделей), — канон, не мусор. Удаляет человек, после dead-code-audit.

## Формат артефакта ds-precheck.md

Используй ровно этот шаблон:

```markdown
# DS-precheck: <имя прототипа> против MLE PEP8

Источник прототипа: <path>
Прочитан prototype-analysis.md: да/нет
Версия mle-pep8.md: <дата/первые строки заголовка>

## Сводка
OK: N | N/A: N | Ф (форма): N | П (поведение): N | О (оптимизация): N

## Класс П — решение человека ДО переноса
| # | Правило | Где (файл:строка) | Что нарушено | Почему меняет поведение | contract-touch? |
| П1 | 1.7 | <module>.py:NN | except Exception → [] | глушит сбой, прототип падал бы | нет |
...
Для каждой П-находки — два варианта:
  (1) изменить поведение → создать отдельную approved behavior-change задачу;
      только она меняет intentional_deviations и golden с provenance;
  (2) сохранить поведение прототипа → зафиксировать как known deviation от
      MLE PEP8, команда принимает.
Решает человек на чекпоинте.

## Класс Ф — требования к owning capability-slice (контракт остаётся зелёным)
| # | Правило | Где | Что сделать | Owning capability | Ловушка? |
...

## Cleanup / optimization ledger (класс О, не блокирует)
| # | Правило | Где | Что сделать после parity | Почему отложено | Статус |
| О1 | ... | ... | ... | не относится к сохранению поведения | deferred |
...

## Что это открывает (future-fit, НЕ перенос)
- 1.13 + File IO в логике → architecture/design эпик target data boundary
- ...

## OK / N/A (для полноты)
Правила, где прототип соответствует или правило неприменимо: <список номеров>.
```

## Как находки текут дальше

- **Ф** → в `harness-prototype-plan` (A3) как acceptance owning
  capability/foundation slice. Несколько связанных Ф-находок объединяются с
  переносимым поведением; находка сама по себе не создаёт T-NNN.
- **П** → решения человека на чекпоинте. «Изменить» создаёт отдельную задачу
  после исходного contract/golden baseline; «сохранить» попадает в реестр
  implementation smells/known deviations. Нельзя переснять oracle внутри задачи
  переноса, чтобы сделать её зелёной.
- **О** → остаётся в cleanup/optimization ledger до зелёного prototype parity.
  После parity отдельный planning pass может осознанно поднять выбранные пункты
  в backlog. Автоматически создавать по одному backlog task на находку нельзя.

## Hard limits

- НЕ менять код прототипа. Только читать и классифицировать.
- НЕ применять ни одной правки по правилам. Все находки — в `ds-precheck.md`.
- НЕ удалять «мёртвый» код. 1.12 — только сигнал; решает человек после
  dead-code-audit (пустой каркас, заданный шаблоном команды, ≠ мусор).
- НЕ переписывать промпты «для чистоты» (1.6/1.8) — это меняет SHA256 контракта.
  Только заводить находку класса П.
- НЕ редактировать `docs/harness/mle-pep8.md` и другие конвенции (read-only).
- При сомнении Ф/П — ставить П и выносить человеку.
- НЕ считать зелёный happy path доказательством эквивалентности error handling:
  сравнивать exceptions, terminal state, retries и side effects.
- НЕ создавать task-per-finding: Ф прикрепляется к owning slice, О остаётся в
  ledger, отдельная П-задача появляется только после явного решения изменить
  поведение.

## Запуск

> Выполни harness-ds-precheck по прототипу <path>. Правила: docs/harness/mle-pep8.md.
> Опирайся на prototype-analysis.md. Ничего не правь — собери ds-precheck.md.

- Каждая П-находка несёт два варианта решения.
- Раздел «что это открывает» заполнен (или явно пуст).
