# Выполнение через watcher

Цикл: создать запрос → дождаться отчёта → разобрать фактический результат.
Watcher синхронизирует исходники, при необходимости готовит окружение, выполняет
команды и возвращает отчёт. Первая подготовка может занять несколько минут.

До нового запуска `harness-pre-commit-check` определяет, достаточно ли прежнего
подтверждения при неизменных входах. В таком случае верни исходный отчёт и
основание его применения, не создавая запрос и не меняя версию прежнего запуска.
Сам watcher не оценивает пригодность старой проверки для изменённого кода.

## 1. Выбрать команды и проверить допустимость

Бери команды из `task.acceptance` (в сохранённом определении —
`acceptance_criteria`), командных правил или запроса пользователя. Не выдумывай
неизвестную команду. Комментарии в создаваемых вспомогательных скриптах пиши
по-русски; не прячь в них запрещённые действия.

Watcher — средство проверок, не канал чтения окружения рабочей станции.
Не читай и не печатай значения переменных окружения, `.env*`, ключи,
пароли и хранилища секретов. Запрещены `env`, `printenv`, чтение `.env` через
`rg`/`grep`/`cat`, вывод переменных и прямые обращения к `os.environ`/
`process.env` ради раскрытия значений. Имена настроек бери из кода и документов.
`.env.example` допустим только по действующим правилам доступа.

Допустимы проверка наличия с фиксированным статусом без значения, обычный
разрешённый запуск приложения без вывода секретов и проверка явно перечисленных
несекретных настроек. Даже временно не помещай секрет в `cmd` или `context`:
запрос, вывод и отчёт сохраняются для аудита.

Watcher 0.7 использует фильтр команд, не песочницу ОС. Он отклоняет явные
сетевые команды (`curl`, `wget`, `ssh`, сетевые операции Git), удаление
(`rm`, `find -delete`, `git clean`) и чтение секретов. Не обходи фильтр другим
интерпретатором, Makefile, тестом или скриптом. Обычные тесты и сборка разрешены,
но их внутренние действия выполняются с правами пользователя и не изолируются.
Старый `--protected` не добавляет защиту. Сохранённая владельцем команда
установки работает без сети; отсутствующие пакеты готовит владелец.
Настройка: `<harness_kit>/harness-watcher/SETUP-GUIDE.md`.

Форма команды: `{"cmd": "make test", "cwd": "."}`. Путь `cwd` относителен
корню целевого репозитория. Команды одной проверки с одинаковыми условиями
синхронизации, окружения и разрешений объединяй в один запрос в нужном порядке.
Разделяй запросы только при разных условиях либо зависимости следующей команды
от полученного результата. Не делай отдельный обмен для каждого теста.

## 2. Синхронизация и файл закреплённых зависимостей

- `sync: "pull"` — получить исходники целевого репозитория на рабочую станцию
  перед выполнением. Обычно нужен для тестов, проверки стиля и сборки.
- `sync: "none"` — выполнять без синхронизации, например проверку версии среды.
- `sync: "push"` и `"both"` запрещены. Отчёты возвращаются отдельно;
  обратного переноса всего дерева нет.

Первый запрос нового профиля с автоподготовкой требует `pull`, даже для команды
версии: установке нужны исходники. `none` не является обходом подготовки.
При ошибке `pull` команды не должны выполняться на устаревшем зеркале.

Если отсутствующий или устаревший `uv.lock` мешает автоматическому
`uv sync --locked`, а изменение зависимостей разрешено, запрос обслуживания
может содержать только `{"cmd": "uv lock", "cwd": "."}`. Допустимы
`--offline` и `--check`, но `--check` ничего не исправляет. Не объединяй эту
команду с установкой или тестами через `&&` либо второй записью. В корне уже
должен существовать `pyproject.toml`; запреты сети сохраняются.

Не рассчитывай вернуть изменённый `uv.lock` автоматически: `push`/`both`
недоступны, а следующий `pull` может заменить локальный результат. Предпочти
разрешённую среду целевого репозитория либо согласованный перенос именно этого
файла с проверкой. Дамп содержимого и обход фильтра недопустимы. Когда проверенный
файл появился в цели, отправь обычный запрос с `pull`. `environment.status:
maintenance` подтверждает только обслуживание; следующий запрос подготовит
среду заново. Старый TOML-режим может не поддерживать автоподготовку.

## 3. Создать уникальный запрос

ID: `{timestamp}-{task_id}-{attempt}` либо `{timestamp}-manual-{attempt}`.
Время UTC — `YYYYMMDDTHHMMSSffffffZ`; попытка — `a1`, `a2` и далее.
Разрешены только `[A-Za-z0-9._-]`, без двоеточий и разделителей путей.
Перед записью убедись, что запрос и отчёт с таким ID отсутствуют.
Никогда не переиспользуй ID.

Файл: `docs/harness/exec-requests/{request_id}.json`.

```json
{
  "request_id": "20261016T090000123456Z-T-001-a1",
  "task_id": "T-001",
  "commands": [
    {"cmd": "make test", "cwd": "."}
  ],
  "timeout_seconds": 600,
  "stop_on_failure": true,
  "sync": "pull",
  "context": {
    "branch": "feature/T-001-config",
    "purpose": "Проверка изменённого поведения перед коммитом",
    "verification_level": "scoped"
  }
}
```

`timeout_seconds` относится к цепочке команд без синхронизации и подготовки;
по умолчанию 600. Обычно сохраняй `stop_on_failure: true`.
В `context` можно добавить известные ожидаемые значения `tree_fingerprint`,
`lock_fingerprint`, `execution_profile`, `commands_fingerprint`. Неизвестное
поле пропусти, не подставляй выдуманное значение.

`commands_fingerprint` — SHA-256 упорядоченного массива команд с нормализованным
POSIX `cwd`, сериализованного JSON с `sort_keys=true`, разделителями `,`/`:`.
`execution_profile` бери только из `evidence.observed` прежнего отчёта того же
профиля. Фактический ключ всегда вычисляет watcher.

Повторное использование того же запуска требует совпадения дерева, файла
версий зависимостей, профиля и упорядоченного списка команд, а также успешных
синхронизации и исполнения. Ветка, коммит или ID задачи не заменяют этот ключ.

## 4. Дождаться отчёта

Вызывай `tasks-mcp.wait_for_report` для одного созданного ID. Общий срок ожидания:
подготовка среды + время команд + запас доставки. Для подготовки используй
известный несекретный `environment.timeout_seconds`; если режим неизвестен —
600 секунд. Например, 600 + 600 + 60 = 1260 секунд. Подготовка может повториться
при изменении входов. Для подтверждённого режима без автоподготовки или
отдельного обслуживания `uv.lock` это время не нужно.

Жди короткими вызовами, обычно 30–60 секунд, сохраняя общий срок.

- `status: ok` и `report` — разбирай результат.
- `status: timeout` — отчёт ещё не получен. Это не таймаут команды и не
  неудачная попытка теста; продолжай ждать тот же ID.
- `status: error` — проверь существование запроса и правильность путей.

После общего срока проверь наличие парного отчёта и безопасные признаки работы
доставки. Пока исход неизвестен, не создавай дубликат и не меняй статус задачи
как после упавшего теста. Решение человека нужно только при действительно
недостающем доступе или выборе. Не удаляй запросы и отчёты вручную.

## 5. Разобрать фактический результат

`report.overall_status`: `success` — команды успешны; `failure` — ошибка команды;
`timeout` — команда превысила срок; `error` — ошибка организации выполнения.
Подробности находятся в `report.results`: `exit_code`, `stdout`, `stderr`,
`duration_ms`. Секретный вывод не копируй в новые отчёты или MCP.

Ошибки до команд не являются падением тестов:

- `environment.status: error` или `sync.push.reason: environment_failed` —
  не удалась подготовка;
- `duplicate_request_id`, `invalid_request_identity`,
  `idempotency_state_unavailable` — ошибка идентичности/учёта запроса;
- причина `command policy` или прежняя `secret-safety policy` — фильтр
  не разрешил команду;
- ошибка `pull` — нужные исходники не получены, исполнение недопустимо.

Для них не вызывай `record_attempt`. Выясни причину и исход старого запроса,
исправь разрешённую часть и только затем создай новый ID. Отказ фильтра нельзя
обходить; замени диагностику безопасной проверкой наличия или несекретных полей.
`ready`/`reused` подтверждают подготовку, `maintenance` — обслуживание,
`disabled` — отключение подготовки, но не успешные тесты.

Подтверждение, пригодное для повторного использования, содержит фактический
`evidence.observed`, безопасный `context`, результаты синхронизации и исполнения.
`requested_matches.<field>: false` означает несовпадение; `null` — ожидаемое
значение не передавалось. Успешный первый запуск с успешным `pull` и без `false`
не повторяй лишь ради `requested_matches.all=true`. Для следующего применения
сравни требуемый ключ с `evidence.observed`. Отчёт без фактического ключа
используй только для диагностики.

Только для связанной задачи и фактического `failure`/`timeout` команды вызови:

```text
tasks-mcp.record_attempt(repo_path, task_id,
  command=<упавшая команда>, exit_code=<её код>,
  error_output=<ошибка без секретов>)
```

При `action: stop` прекрати повторы и вызови `report_blocker`.
При `continue` исправь причину и создай новый ID. Для ручного запроса без задачи
не выдумывай ID для MCP: верни пользователю отчёт и безопасный следующий шаг.
Если секрет попал в вывод, не размножай его; сообщи об инциденте и необходимости
смены секрета, если он мог сохраниться в запросе, отчёте или журнале.

## Результат

Не держи больше одного незавершённого запроса. Верни ID и путь отчёта,
результат команд, подтверждённый ключ либо `not reusable` и следующий шаг.
Успешно обработанный запрос watcher переносит в `exec-processed/`, отчёт
возвращает в `docs/harness/exec-reports/`. При обязательном watcher не обходи
его прямым локальным запуском.
