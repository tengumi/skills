# Извлечь правила подготовки к эксплуатации

## Результат

Создай или дополни `docs/harness/team-patterns-production.md`. Каждый факт сопровождай путём источника и его ролью:

- шаблон команды задаёт обязательную структуру и используемые технологии;
- готовый сервис показывает способ реализации, но может содержать устаревшие решения;
- пример выпуска подтверждает сборку и CI, но не заменяет зависимости и логику целевого агента;
- пример интеграции показывает конкретное подключение, а не реквизиты чужого сервиса.

Не объединяй эти роли в один безусловный эталон. Используй только источники, прямо предоставленные для задачи. Если сведения уже актуальны, переиспользуй их.

## Что прочитать

Сначала прочитай относящиеся к задаче документы команды в `docs/harness/`: `architecture.md`, `configuration.md`, `conventions.md`, `dev-setup.md`, `project_structure.md`, `rules.md`, `cicd.md`, если они есть. Не переписывай их: этот скилл заполняет недостающие сведения о запуске, сборке, сопровождении и интеграциях.

В названном шаблоне и примерах изучай только соответствующие части. Для интеграции прочитай всю цепочку: настройки → создание клиента → регистрация зависимостей → использующий сервис → тесты, а также декларации зависимостей и файл зафиксированных версий.

## Что зафиксировать

| Область | Проверяемые сведения |
|---|---|
| Сборка и контейнер | Команды установки и сборки, базовый образ, `WORKDIR`, `COPY`, команда запуска, включение ресурсов |
| CI/CD | Общая библиотека и её версия, функция конвейера, этапы, Jenkins/ArgoCD/Sonar, обязательные поля DevSecOps |
| Названия сервиса | Репозиторий, сервис, пакет, модуль Python, участник рабочей области, образ, задание CI, очередь, схема БД, генерируемый клиент |
| Зависимости | Корневые и проектные декларации, правила `uv.lock`, динамические импорты, версии общих библиотек |
| Готовый пакет | Промпты, настройки, OpenAPI, скрытые импорты, `env.py` и весь применимый каталог миграций `versions/` |
| Процессы | Реальные точки входа API, обработчика задач, планировщика и инициализации БД; регистрация задач и передача данных через контейнер зависимостей |
| Проверки состояния | Точные адреса проверок работоспособности, готовности и метрик; механизм общей библиотеки; отдельные проверки фоновых процессов |
| Журналы и телеметрия | Инициализация, передача контекста запроса, исключение чувствительных данных, охваченные процессы и библиотеки |
| Автоматические проверки | Действующие команды тестов, линтера, сборки и проверки перед коммитом; применимые пути |
| Клиенты API | Источник и версия контракта; готовый SDK либо генератор, его версия, команда, результат генерации и правила хранения |
| База данных | Владелец, схема, `script_location`, список миграций, `heads`, правила применения при запуске, безопасный способ проверки |
| Общая библиотека | Готовые настройки, клиенты, создание зависимостей, инициализация приложения, журналы, метрики и проверки состояния |

Для каждого внешнего подключения дополнительно запиши:

- пакет SDK, допустимые версии и фактически установленную версию;
- протокол, доступ при локальном запуске и в кластере;
- время жизни объекта клиента отдельно от активного соединения или сессии;
- кто и когда открывает ресурс, кто ожидает его закрытия;
- обязательность подключения для запуска и готовности процесса;
- кто выполняет повторные попытки и где заканчивается область ошибки;
- источник каждого решения.

Объект в области `APP` не означает разрешение открывать сеть при импорте или запуске. Раннее соединение допустимо только по явному контракту процесса.

## Примеры интеграций

Сопоставь выбранный пример с [картой интеграций](../harness-production-readiness/references/integration-patterns.md) и только нужным сценарием. Отметь тип настроек, префикс, прямую зависимость от SDK, передачу контекста, владельца ресурса и отличия целевого сервиса.

Разделяй наблюдаемое решение, предлагаемую адаптацию и выполненную проверку. Если версия исходника неизвестна, так и запиши: это не запрещает изучить способ подключения, но не доказывает чистоту Git или работоспособность. Не копируй опасное закрытие ресурсов, неизвестные операции и тестовые подмены только потому, что пример назван правильным.

## Порядок работы

1. Изучи существующие командные документы и разрешённые источники.
2. Выпиши факты с путями и ролями источников. Неизвестное оставь явно неизвестным.
3. Конфликты оформи как «вопрос → источник → значение → решение или `OPEN`». Существенный конфликт передай владельцу, не выбирай молча.
4. Сохрани результат в `docs/harness/team-patterns-production.md` с разделами по применимым областям из таблицы.
5. В конце перечисли недостающие сведения и данные, которые должен дать владелец: например, идентификатор сервиса, пространство имён или имена секретов.

Подробные операции и преобразования данных храни в `data-boundaries.md`; здесь достаточно ссылки. Для общих конвенций нескольких репозиториев предназначен `harness-extract-patterns`, а не этот скилл.

## Ограничения

- Не изменяй код и документы команды во время извлечения сведений.
- Не придумывай реквизиты выпуска и не переноси чужие идентификаторы как целевые значения.
- Не читай и не копируй значения секретов. Нужны только названия настроек и правила передачи.
- Не заменяй список зависимостей целевого агента списком из примера выпуска. Сравни различия, сохрани зависимости его кода и согласованные версии общих пакетов.
- Запись вида `pkg>=X` не доказывает совместимость со следующим основным выпуском пакета. Нужны установленная версия и подтверждённый диапазон либо явно отмеченная непроверенная совместимость.

Результат используют `harness-production-plan`, `harness-production-readiness` и `harness-team-layout-alignment`. Извлечение сведений само по себе не подтверждает готовность к выпуску.
