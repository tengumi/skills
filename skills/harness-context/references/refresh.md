# Refresh существующего harness-контекста

Использовать только при `mode=refresh`. Цель — синхронизировать навигационную
карту с кодом, не переписывая знания команды.

## 1. Определить baseline

Найти последнюю актуализацию по `<!-- harness-updated: YYYY-MM-DD -->` или
последнему коммиту `AGENTS.md`. Если доказуемой точки нет, взять только
подтверждённую пользователем ревизию/период; не угадывать полный diff.

Собрать изменения структуры, entrypoints, build-файлов, зависимостей и API.
Пустая или тривиальная дельта означает «обновление не требуется» без записи.

## 2. Разделить ownership

- `auto-owned`: только явно маркированные auto-секции AGENTS.md или, при
  отсутствии маркеров, стек, карта кода, быстрые команды и ссылки;
- `human-owned`: назначение, доменные соглашения, запреты и любые сомнительные
  секции;
- `team-owned/read-only`: `architecture.md`, `configuration.md`,
  `conventions.md`, `dev-setup.md`, `project_structure.md`, `rules.md`,
  `mle-pep8.md` и иные документы, обозначенные командой.

При сомнении считать секцию human-owned. Конфликт кода с team docs оформить
proposal владельцу, не править документ под текущее состояние кода.

## 3. Составить дельта-план

Для каждой auto-owned секции показать точное изменение и источник факта.
Отдельно перечислить файлы, которые останутся нетронутыми. Дождаться approval
до записи.

Не включать в план `docs/harness/tasks.json`: lifecycle задач ведёт tasks-mcp,
а новые задачи создают planning-skills.

## 4. Сделать backup и изменить только утверждённое

Перед записью каждого файла создать
`docs/harness/.backups/<filename>-<timestamp>`. Обновить только утверждённые
auto-owned фрагменты; сохранить порядок, комментарии и ручные дополнения.

Не создавать неизвестные Makefile targets. Изменение build/CI/runtime docs без
явного auto-owned marker и approval остаётся proposal.

После изменения поставить или обновить
`<!-- harness-updated: YYYY-MM-DD -->` в AGENTS.md.

## 5. Чистый maintenance handoff

Проверить diff только контекстных файлов, отсутствие секретов и неизменность
team docs/tasks lifecycle. Оформить это отдельным maintenance handoff, чтобы
изменения документации не попали в следующую feature/port задачу.

Отчёт должен перечислить изменённые секции, backup paths, пропущенные proposals
и факт отсутствия изменений в `tasks.json` и team-owned документах.

## Hard limits

- Не переписывать AGENTS.md целиком.
- Не удалять ручные правки или неизвестные пути.
- Не писать до показа плана и approval.
- Не редактировать team-owned документы даже ради согласования с кодом.
- Не обновлять task status, attempts, evidence или completed sections.
- Не оставлять refresh-артефакты в dirty diff следующей задачи.
