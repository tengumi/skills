# Контекст репозитория

Сделай так, чтобы Кодовый агент находил назначение проекта, правила, команды
и текущую задачу в самом репозитории. Не дублируй всю документацию в `AGENTS.md`.

## Выбор режима

| Режим | Когда применять | Что можно записать |
|---|---|---|
| `bootstrap-minimal` | Есть командный шаблон, документы или точный `team_docs_source` | `AGENTS.md`, отсутствующая пустая очередь; из указанного источника — только отсутствующие командные документы |
| `bootstrap-full` | Подтверждено отсутствие официальных командных документов | После показа плана — отсутствующие документы проекта и необходимые рабочие команды |
| `refresh` | Контекст уже существует | Только подтверждённые изменения разделов, которыми управляет Harness |

Для `refresh` полностью прочитай [references/refresh.md](references/refresh.md)
и выполни его вместо первоначальной подготовки ниже.

Вызов `harness-lead` разрешает минимальную подготовку в указанном целевом
репозитории. Отдельное подтверждение нужно только при конфликте источников,
совпадении имён с различным содержимым или выходе за уже разрешённый объём.
Отсутствие `AGENTS.md` и пустой очереди само по себе не причина останавливаться.

## Источники и сохранность

- `architecture.md`, `configuration.md`, `conventions.md`, `dev-setup.md`,
  `project_structure.md`, `rules.md`, `mle-pep8.md` и иные предоставленные
  документы команды доступны только для чтения. Несогласованность с кодом
  опиши владельцу, не исправляй документ под текущий код.
- При `team_docs_source` копируй только отсутствующие файлы. Совпавшее имя
  с отличающимся содержимым — конкретный вопрос, а не разрешение перезаписать.
- Запиши источник и SHA-256 скопированных файлов в
  `docs/harness/team-docs-source.json`. Не включай секреты и персональные
  абсолютные пути; используй понятную метку источника.
- Не читай `.env`, значения переменных окружения, ключи и итоговую конфигурацию
  с секретами. Имена настроек и безопасные проверки наличия допустимы.

## Что изучить

Прочитай README, файлы зависимостей, структуру первых двух уровней, точки входа,
представительные тесты, настройки автоматических проверок и относящиеся к
задаче документы. Определи, один это сервис или несколько связанных проектов.

Если есть граф или другой управляемый процесс, установи точку входа, основные
шаги, переходы, состояние и внешние вызовы. Описывай устройство процесса,
а не пересказывай каждую строку бизнес-логики.

Для связей между проектами найди реальные HTTP/gRPC-вызовы, очереди, события
и общие библиотеки. В минимальном режиме неизвестные подключения, параметры
развёртывания и другие сведения этапа B запиши как пробелы: они не должны
задерживать создание навигации или чтение прототипа. Уточняй только то,
без чего нельзя выбрать целевой репозиторий или разрешить конфликт источников.

## `AGENTS.md`: не более 120 строк

Создай или дополни навигационную карту:

1. Назначение проекта — 2–3 предложения на основании источников.
2. Стек и установленные версии основных компонентов.
3. Только существующие команды установки, запуска, тестов и проверок.
4. Карта кода: путь и одна строка об ответственности.
5. Несколько конкретных командных соглашений и запретов.
6. Порядок работы с задачей.
7. Ссылки только на реально существующие подробные документы.

В порядке работы отрази:

- прочитать `AGENTS.md` и текущую задачу;
- через [harness-work-session](../harness-work-session/SKILL.md) взять одну
  задачу в работу; её состояние изменяет Tasks MCP;
- зафиксировать исходное состояние и выполнить только критерии этой задачи;
- провести назначенные проверки; watcher нужен только по правилам среды
  или явному запросу, а не автоматически в каждом проекте;
- пройти [harness-pre-commit-check](../harness-pre-commit-check/SKILL.md)
  и передать `submit_task` подтверждающие результаты.

Не записывай `make verify`, если такой команды нет. Не запускай установку,
сборку или все тесты только ради документирования существующих команд.

## Первоначальная очередь

Если `docs/harness/tasks.json` отсутствует, создай пустую очередь:

```json
{
  "version": "1.0",
  "last_updated": "<текущая дата>",
  "current_sprint": [],
  "completed_sprint": [],
  "backlog": [],
  "discovered_bugs": [],
  "tech_debt": []
}
```

План задач создаёт профильный скилл. В определении задачи критерии находятся
в `acceptance_criteria`; ответ Tasks MCP может представлять их как
`task.acceptance` — это одно содержание, не две независимые версии.
Уже выданные разрешения хранятся в `approvals` с областью действия, источником,
владельцем и датой. Список `files_hint` сам по себе разрешением не является.

Не меняй вручную `status`, `claimed_by`, `attempts`, `evidence` существующих
задач. Не затирай очередь.

## Полный режим без официальных документов

Сначала покажи план отсутствующих документов. Можно создать:

- `architecture.md` — компоненты, поток данных, граф, внешние зависимости
  и подтверждённые архитектурные решения;
- `conventions.md` — стиль, именование, ошибки, журналирование и тестирование;
- `dev-setup.md` — требования, установка и воспроизводимые команды;
- `cicd.md` — существующие проверки, сборка и развёртывание;
- `tasks.json` — очередь по приведённой схеме.

Не перезаписывай существующее знание команды и не выдумывай отсутствующие
решения. `Makefile` меняй только в явно разрешённом объёме полного режима;
каждая команда должна работать. Неизвестная команда — пробел, а не пустая
цель с `TODO`. Минимальный режим не меняет `Makefile`.

## Результат

Покажи выбранный режим, фактически созданные, скопированные, изменённые
и сохранённые файлы; количество строк `AGENTS.md`; существенные пробелы
и следующий шаг. Не объявляй отсутствующий документ созданным.
Проверь ссылки, сохранность ручных дополнений, командных документов
и состояния задач. Верни управление [harness-lead](../harness-lead/SKILL.md).
