# Обзор репозиториев

Помоги выбрать, с какого проекта начать внедрение Harness. Это инвентаризация,
а не проверка готовности сервиса к выпуску и не разрешение менять его код.

## Вход и границы

- Используй указанный корень рабочей папки; если его нет — текущую папку.
- Обследуй реальные каталоги проектов. Не запускай сервисы и не меняй их файлы.
- Не открывай `.env`, ключи, сертификаты, хранилища секретов и вывод с их значениями.
- Не включай зависимости, кеши и результаты сборки: `node_modules/`, `.venv/`,
  `venv/`, `__pycache__/`, `target/`, `dist/`, `build/`, содержимое `.git/`.

## Что собрать

Найди проекты по `.git`, `pyproject.toml`, `package.json`, `pom.xml`,
`build.gradle`, `build.gradle.kts`, `go.mod`, `Cargo.toml`, `Dockerfile`.
Для списка файлов предпочитай `rg --files`.

Для каждого проекта запиши:

| Поле | Источник |
|---|---|
| `name`, `path` | Имя каталога и путь относительно рабочей папки |
| `stack` | Язык и библиотеки из файлов зависимостей |
| `size` | `small`: менее 20 исходных файлов; `medium`: 20–100; `large`: более 100 |
| `has_tests` | Каталоги и файлы тестов |
| `has_ci` | Файлы автоматических проверок, например Jenkins или GitHub Actions |
| `has_agents_md` | Наличие `AGENTS.md` |
| `has_makefile` | Наличие `Makefile` |
| `has_docs` | Хотя бы один документ в `docs/harness/` |
| `last_commit` | Дата последнего коммита, если доступна; иначе `null` |
| `purpose` | Подтверждённое краткое назначение из README; иначе неизвестно |

Определяй стек по фактам: Python — `pyproject.toml`, `setup.py` или
`requirements.txt`; Java — Maven/Gradle; Go — `go.mod`; Rust — `Cargo.toml`.
Для `package.json` различай веб-интерфейс с React/Vue/Next и серверный Node.js.
Один Dockerfile без прочих признаков означает `docker-only`, не известный язык.

## Оценка и файлы результата

`harness_score` — сумма пяти признаков `has_tests`, `has_ci`, `has_agents_md`,
`has_makefile`, `has_docs`, по одному баллу за каждый. `harness_gaps` перечисляет
отсутствующие средства. Балл отражает только наличие файлов: он не доказывает
качество тестов, работоспособность команд, сохранение поведения или готовность
к промышленной эксплуатации.

Создай в корне обследованной папки `workspace.json`:

```json
{
  "scanned_at": "<время обследования>",
  "workspace_root": "<корень рабочей папки>",
  "services": [],
  "summary": {
    "total_services": 0,
    "stacks_found": [],
    "harness_ready": 0,
    "partial": 0,
    "no_harness": 0,
    "scanned_paths": []
  }
}
```

В `services` помести записи со всеми перечисленными полями и оценкой.
Для совместимости группируй баллы 4–5 в `harness_ready`, 2–3 в `partial`,
0–1 в `no_harness`. В человекочитаемом отчёте называй эти группы полнотой
подготовки к Harness, а не готовностью к выпуску.

В `workspace-overview.md` покажи сводку, таблицу проектов, точные пробелы
и рекомендуемый порядок внедрения. Учитывай бизнес-значимость, активность
разработки, наличие тестов и риски; не объявляй самый частый стек лучшим.
Не выдумывай проекты, даты, владельцев или назначения.

## Передача результата

Сообщи количество проектов, распределение оценок и до трёх подходящих первых
кандидатов с причинами. Для выбранного проекта предложи
[harness-context](../harness-context/SKILL.md).
Не запускай изменения во всех найденных репозиториях и не делай коммиты
лишь на основании обследования.
