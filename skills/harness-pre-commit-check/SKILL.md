# Проверка перед коммитом

Задача — доказать, что конкретные изменения можно безопасно зафиксировать,
а не просить разрешение на каждый коммит.

## Режим и разрешённый объём

- `task` — занятая задача; объём определяется критериями, разрешённым планом
  и записанными решениями.
- `preflight` — подготовительные документы и явно разрешённые изменения
  `harness-lead` до первой задачи.
- `direct-review` — только проверка по запросу пользователя, без коммита.
- `direct-commit` — прямой запрос на коммит указанного изменения.

Действуют исходный запрос на реализацию/исправление, занятая задача, утверждённый
план, `task.approvals` либо явное разрешение текущего запуска. Они не расширяют
объём друг друга. Более узкое или позднее ограничение, запрет коммита и режим
только проверки имеют приоритет. Разрешение локального коммита не разрешает
внешние вызовы, развёртывание, разрушительные действия или общую БД.

## Что проверить

### Ветка, состав и назначение изменений

Используй `git branch --show-current`. Для задачи допустима
`feature/<task.ticket или task.id>[-краткое-описание]`; для подготовки —
`feature/T-000[-краткое-описание]` либо точная согласованная ветка.
Описание выбери сам по задаче. Не требуй Jira ID или `NOJIRA`.
В защищённой ветке коммит запрещён.

Если индекс непустой, проверяй подготовленные к коммиту изменения; иначе —
изменения рабочего дерева. Свяжи каждый путь и существенный фрагмент с задачей.
Подготовка может включать `AGENTS.md`, документы анализа и плана,
определения/зависимости/разрешения в `tasks.json` и другие явно разрешённые пути.
Текущие статусы MCP при `out_of_band` не входят в коммит реализации.

Не включай чужие изменения, постороннюю чистку, массовое форматирование,
сырые файлы обмена watcher и результаты исполнения. Очевидно лишний собственный
путь убери из индекса, сохранив файл. Если принадлежность действительно
неоднозначна, уточни точные пути. Не считай всё изменённое дерево разрешённым.

### Защищённые файлы

Возьми список из действующих правил репозитория. Для CI, миграций, сборки,
зависимостей и сгенерированных файлов найди разрешение с подходящим объёмом.
Утверждённый план переименования покрывает перечисленные пути и соответствие
имён. `files_hint` само по себе не является разрешением.
Останови только выход за объём, новое поведение или внешнее действие без
разрешения. Уже согласованные безопасные локальные изменения не подтверждай снова.

### Минимально достаточная проверка

| Изменение или `verification_level` | Что требуется |
|---|---|
| Только документы/подготовка | `git diff --check`, разбор и проверка по применимой схеме изменённых JSON/YAML, проверка отсутствия секретов/результатов исполнения |
| `scoped` | стиль, импорт и тесты изменённого поведения |
| `capability` | предыдущие проверки и цельный функциональный контракт |
| `runtime` | предыдущие проверки и настоящий процесс, рабочая сборка зависимостей и время жизни ресурсов |
| `bundle` | чистая установка, полная командная проверка, сборка, состав пакета и запуск исходных/собранных процессов |
| Зависимости ниже `bundle` | необходимая совместимость разрешённых версий и импорта |
| Миграции | состав исходных/собранных ревизий и разрешённая проверка без изменения общей БД |
| Внешнее подключение | безопасные контрактные проверки с подменой транспорта; реальные вызовы только отдельно разрешённые |

Не дублируй команды, уже входящие в `make verify`. Но общий успешный запуск
не заменяет специальную проверку, если она нужна. Подтверди по выводу, что
нужные тесты действительно выполнены, не исключены и не пропущены.
Для `runtime` нужен настоящий экспорт приложения и рабочая сборка зависимостей,
а не созданный только в тесте список подмен. Перед итоговой сборкой проверь
актуальность README/инструкции эксплуатации и ресурсы установленного пакета.

Применимой сборкой в одном `plan_id` владеет ровно одна задача. Не запускай
чистую установку и сборку заново для каждой небольшой правки. Несогласованное
требование упаковки верни планировщику, не меняя уровень задачи молча.

Отчёт допускается использовать повторно при совпадении ключа
`tree/lock/profile/commands` либо если проверенное дерево соответствует предку
HEAD и все потребляемые входы неизменны. Учитывай код и зависимости, манифесты,
файл закреплённых версий, профиль, команды, контракты и генераторы.
Сохрани исходный отчёт и ключ; отдельно опиши основание применения к текущему
состоянию. Не выдавай его за новый запуск. Если входы неизвестны или поведение
вызывает сомнение, повтори нужную проверку её уровня. Новая сессия или коммит
без изменения этих входов сами по себе не требуют повтора.

При рискованном изменении выполнения проверь результат независимого разбора
из `harness-work-session` и тесты выявленных расхождений. Недостающую или
неуспешную проверку сначала выполни/исправь в текущем объёме; это не
автоматическая остановка для решения человека.

### Секреты, незавершённый код и конвенции

Проверяй добавленные строки и изменённые пути штатной защитой репозитория либо
точечным поиском без раскрытия значений. Не читай `.env` и хранилища секретов.
Исключи реальные ключи/токены/пароли, закрытые ключи сертификатов, сырые логи,
тексты документов/ответов моделей с закрытыми данными и необезличенные примеры.
Для шаблона `rg`, начинающегося с `-`, ставь `--` перед шаблоном.
При находке сообщи только путь и строку, не значение; такой материал нельзя
коммитить даже после подтверждения.

Проверь отладочные выводы, точки останова, необоснованный закомментированный код,
непривязанные TODO/FIXME/HACK/XXX, подавленные исключения и командный стиль.
Подтверждённую заглушку шаблона или учтённый технический долг можно оставить
с объяснением. Комментарии в изменяемых скриптах пиши по-русски.
Собственный дефект исправляй внутри текущей задачи; независимый передай
планировщику. Не сдавай задачу, если дефект мешает её критериям.

### Сообщение и размер коммита

Следуй формату репозитория. Обычно идентификатор — `task.ticket`, иначе
`task.id`, для подготовки — `T-000`; текст краткий, в повелительном наклонении,
по фактическим изменениям. Не спрашивай формат, если он известен из правил
или истории.

Больше 500 строк или 10 файлов — повод внимательнее проверить, не обязательная
остановка. Независимые изменения можно разделить; связную генерацию или
подготовку сохрани одним коммитом с указанием размера.

## Решение

После всех успешных проверок при действующем разрешении верни:

```text
status: PASS_AUTO
commit_authorized: true
commit_message: <сообщение>
evidence_reused: <исходные отчёты и основание повторного использования либо none>
verification_key: <исходный tree/lock/profile/commands>
warnings: <неблокирующие замечания>
```

В `task`, `preflight`, `direct-commit` вызывающий скилл продолжает коммит и
сдачу без дополнительного вопроса. В `direct-review` верни `PASS_REVIEW_ONLY`
и не выполняй коммит.

`BLOCKED` допустим при секрете, неотделимых посторонних изменениях, недостающем
обязательном подтверждении после попытки получить его, защищённом изменении
без разрешения, защищённой ветке или действительно неясном объёме/формате.
Исправимое локально исправляй сам. Решение человека требуется только для
изменения поведения, архитектуры, разрешений или конфликта командных правил.

Верни статус, выбранные изменения, сообщение коммита, использованные результаты,
замечания и точные необходимые действия. Не создавай повторных подтверждений.
