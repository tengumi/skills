# Выполнение одной задачи

Результат — одна завершённая задача, её ветка с одним коммитом и подтверждения
в Tasks MCP. Правила кода находятся в `AGENTS.md` и `docs/harness/`.
Если задача уже `in_progress` и `claimed_by` указывает на текущего исполнителя,
продолжай с места остановки, не занимая её повторно.

## 1. Контекст и выбор задачи

Прочитай `AGENTS.md` и `docs/harness/conventions.md`, если они ещё не прочитаны.
Не создавай отдельную проверку окружения, отчёт или коммит только ради подготовки.
Минимальную проверку команд и исходного состояния включи в текущую задачу.
В непрерывном прогоне перечитывай стабильные документы только после изменения
их содержимого; новая сессия сама по себе не отменяет известные факты.

Если `harness-lead` передал точный `task_id`, определение задачи и свежие статусы
MCP, используй их без повторного выбора. Если передан только ID, получи
недостающие данные до взятия задачи. В самостоятельном режиме вызови
`tasks-mcp.list_open_tasks(repo_path)`; при отсутствии ID покажи список и спроси
выбор. Задачу из чата без ID сначала предложи оформить в очереди.

Проверь `queue_storage_mode`. При `out_of_band` определения находятся в
`tasks.json`, а текущие статусы — в MCP. Режим `tracked` допустим только при
заранее определённом отдельном канале записи состояния: операции MCP не должны
менять `tasks.json` в ветке реализации.

Занимать можно только `open`. Если ID нет в списке, `include_all=true` нужен
лишь для выяснения статуса; не занимай повторно `blocked`, `in_progress` или
`done`, даже если сервер технически позволяет это. Все зависимости `depends_on`
должны иметь `done`. Не выводи зависимости из порядка записей или текста заметок.

Для `harness-eval:prototype-parity` дополнительно обязательны `stage: A` и
`plan_id`. Все остальные задачи этого плана A, включая добавленные позднее,
должны быть завершены. Для каждой проверь `evidence.commit_sha` и
`git merge-base --is-ancestor <commit_sha> HEAD`. Незавершённая задача
`harness-prototype-port` без `plan_id` означает неопределённую границу плана:
сначала исправь определение. Старый `depends_on` не заменяет эту проверку.

## 2. Скилл, режим и разрешения — до взятия задачи

Проверь полное определение `use_skill`/`skill_mode` и критерии готовности.
Для задач B прочитай паспорт и нужную часть `data-boundaries.md`.

| Задача | Что требуется заранее |
|---|---|
| `harness-eval:prototype-parity` | версии прототипа и цели, `prototype-contract.json`, безопасные входы для сравнения; разрешение внешнего вызова только если он нужен |
| `harness-production-readiness:contract` | подключение зарегистрировано, объём ограничен сбором фактов или проектом решения |
| `harness-production-readiness:adapter` | раздел подключения имеет не ниже `MAPPED`; известны операция, версия, авторизация и соответствие полей; существенных конфликтов нет |
| Другой режим `harness-production-readiness` | разрешённый план и нужное разрешение защищённых изменений |
| `harness-eval:live` либо внешний вызов в `stand` | отдельное текущее разрешение на точную среду, данные, вызов и внешние изменения |
| `harness-golden` | понятная задача, доступные источники входов и правильности, контракт и правила данных; готовый `golden-spec.yaml` не обязателен |
| `harness-eval:golden` | выпущенный набор, журнал проверок, хеши и правила данных; отдельное разрешение внешних вызовов при необходимости |

Для `contract` незаполненная техническая карта ожидаема. Для реализации
отсутствующие обязательные сведения, существенный конфликт или несовпадающий
объём разрешения требуют сначала получить контракт или решение.

Разрешение исходного безопасного локального прогона либо подтверждённого плана
действует для всех точно перечисленных зависимостей и защищённых путей.
Не запрашивай его повторно перед веткой, правкой, проверкой, коммитом или сдачей.
Новый вопрос нужен при существенном выходе за объём, конфликте источников или
внешнем действии, включая общую БД и развёртывание.

Многорежимные скиллы требуют точного `skill_mode`:

- `harness-context`: `bootstrap-minimal`, `bootstrap-full`, `refresh`;
- `harness-production-readiness`: `dependency`, `config`, `contract`, `adapter`,
  `process`, `db`, `observability`, `deploy`, `runbook`, `stand`;
- `harness-eval`: `golden`, `prototype-parity`, `live`.

У `harness-golden` режима нет. Старый `harness-eval:synthesize` сначала исправь
отдельной правкой плана на `harness-golden` без режима. Не угадывай режим по
заголовку или файлам. Неизвестный/лишний режим либо конфликт с критериями верни
планировщику. Старое имя без `harness-` исправляй только при однозначном
соответствии точному `name` скилла, отмечая дефект очереди.

## 3. Взять задачу и создать ветку

Для локального Tasks MCP через стандартные потоки используй
[инструкцию взятия задачи](../harness-lead/references/artifact-tools.md): проверка плана, актуальных
определений и зависимостей выполняется до единственного `claim_task`.
Если проверка завершилась ошибкой, не обходи её отдельным вызовом.
После успеха утилиты повторный `claim_task` не нужен.

Если MCP подключён другим способом, выполни те же проверки доступными
инструментами, затем `tasks-mcp.claim_task(repo_path, task_id)`. Не называй
такой путь автоматически защищённым утилитой. Ошибка занятия означает,
что задача не получена; реализацию не начинай.

Нормализованное `task.acceptance` соответствует сохранённому
`acceptance_criteria`; используй один актуальный список, не объединяй разные.
Создай `feature/<task.ticket или task.id>[-краткое-описание]`.
Только префикс `feature/`, в том числе для исправлений. Не работай в защищённой
ветке. Идентификатор задачи заменяет отсутствующий Jira ID.

Передай реализацию скиллу из `use_skill` вместе с точным `skill_mode`.
Если `use_skill` отсутствует, но есть `ported_from`, используй
`harness-prototype-port`. Обычный путь не гарантирует сохранение логики.
Механикой ветки, занятия и сдачи задачи продолжает владеть один исполнитель.

## 4. Реализация

Прочитай `files_hint` или найди относящиеся файлы через `rg`. Проверь реальные
импорты, вызовы, сборку зависимостей и командные правила; не активируй устаревший
код по сходству имени. До первой правки зафиксируй один проверяемый
функциональный результат и минимальное исходное состояние его уровня проверки.
Не запускай полную сборку как универсальную подготовку.

Исходную неисправность не выдавай за свою регрессию и не исправляй заодно.
Она блокирует задачу только если не позволяет доказать её критерии. При
конфликте примеров, реальных сообщений, эталонов и документов покажи версии
и происхождение фактов; останови только затронутое подключение.

Изменяй зависимости без повторного вопроса, если пакет, версия и пути уже
покрыты разрешённым планом. Выход за этот объём требует решения.
Следуй критериям задачи и командному стилю. Комментарии в новых или изменяемых
скриптах пиши по-русски; точные имена API и полей оставляй как в коде.

Ошибку собственной реализации и незакрытый критерий исправляй в этой же задаче.
Независимый дефект передай планировщику; не сдавай задачу, если он мешает её
приёмке. Не создавай новую задачу только из-за нового лога или упавшего теста.
Рутинные пробелы стиля решай по шаблону и соседнему согласованному коду;
спрашивай при изменении поведения, архитектуры или конфликте требований.

При разрешённом делегировании используй доступных в среде субагентов с текущими
настройками модели. Один ответственный сохраняет владение задачей, веткой,
коммитом и сдачей. Не поручай пересекающиеся файлы нескольким исполнителям;
проверяй результат перед объединением. Если такого инструмента нет, продолжай
последовательно, не устанавливая отдельную систему исполнения.

## 5. Проверка по `verification_level`

| Уровень | Проверки |
|---|---|
| `scoped` | стиль, импорты и тесты изменённого поведения |
| `capability` | предыдущие проверки и цельный контракт функционального результата |
| `runtime` | предыдущие проверки и запуск настоящего приложения, рабочих зависимостей и времени жизни ресурсов с разрешёнными подменами внешнего транспорта |
| `bundle` | чистая установка, полная командная проверка, сборка, состав пакета и запуск исходных/собранных процессов |

Новый план обязан задавать уровень. Для старой задачи без него выбери
минимально достаточный по критериям и отметь дефект определения.
В одном плане применимой сборкой владеет ровно одна задача. Не повышай другие
задачи до `bundle` из осторожности; несогласованные требования упаковки верни
планировщику. Для зависимостей ниже `bundle` достаточно нужной проверки
разрешения версий и импорта; для миграций — состава исходных и собранных ревизий
и разрешённой проверки без изменения общей БД.

Вывод запуска должен подтверждать выполнение нужных тестов, а не только наличие
файла в исключённом каталоге. Проверка `runtime` использует реальный экспорт
приложения и рабочую сборку его зависимостей, не ручной список подмен в тесте.

Старый успешный отчёт допустим при полном совпадении ключа
`tree/lock/profile/commands` либо если проверенное дерево соответствует предку
HEAD и все входы этой проверки неизменны. Учитывай код и его зависимости,
манифесты, закреплённые версии, профиль, команды, контракты и генераторы.
Сохраняй исходный отчёт, версию и ключ, отдельно записывая основание применения
к текущему состоянию. Не называй это новым запуском. Если состав входов
неизвестен, повтори затронутую проверку без автоматического перехода к сборке.

При реальной неудаче проверки вызови `tasks-mcp.record_attempt` с командой,
кодом возврата и очищенной от секретов ошибкой. При `action: continue` исправь
причину в согласованном объёме. При `action: stop` прекрати повторы и вызови
`report_blocker`. Ошибки подготовки или доставки watcher не являются падением
теста; следуй `harness-request-exec`.

## 6. Перед коммитом и сдачей

При изменении синхронного/асинхронного выполнения, параллелизма, исключений,
повторов или времени жизни клиента нужна независимая проверка изменения.
Передай проверяющему исходник, изменения и инварианты, не вывод автора
«всё эквивалентно». Проверь порядок, отмену, типы ошибок и закрытие ресурсов.
Расхождение воспроизведи тестом и исправь в текущей задаче. Если второй агент
недоступен, явно отметь ограничение и сделай отдельный проход; не называй
самопроверку независимой. Это не повод для нового согласования или полной сборки.

Выполни `harness-pre-commit-check`. Каждый изменённый путь должен относиться
к критериям задачи. Посторонние изменения не включай; чужую работу не удаляй.
После успеха сделай коммит в формате командных правил без нового вопроса.

Получи `commit_sha` через `git rev-parse HEAD` и сдай задачу:

```text
tasks-mcp.submit_task(repo_path, task_id, evidence={
  "commit_sha": "<sha>",
  "tests_passed": true,
  "branch": "<ветка>",
  "lint_passed": true,
  "notes": "<уровень проверки; исходная версия и ключ; основание повторного использования>",
  "artifacts": ["<относительный путь отчёта>"]
})
```

Указывай только фактически успешные проверки. Если профильный скилл создал
отчёт, добавь его в `artifacts`; для `harness-golden` и `harness-eval` это
обязательно. Не выдумывай новые поля MCP. Коммит текущей задачи не меняет
версию старого запуска. Если нужна приёмка выпуска, до сдачи обязательны
успешные внешние проверки и решение владельца; `APPROVE`/`DEFER`, роль, дата,
объём и ссылка записываются в существующие `notes`/`artifacts`.

При `reject` исправь указанные поля. После `ok` задача имеет `done` и
`completed_sprint` в состоянии MCP. При `out_of_band` исходный `tasks.json`
не обязан менять раздел или статус. Рабочее дерево после сдачи должно быть
чистым; неожиданную запись статусов в отслеживаемый `tasks.json` не включай
вторым коммитом, сообщи о неисправности настройки Tasks MCP.

## Завершение

В самостоятельном режиме сообщи задачу, результат, ветку, коммит и проверки.
Под управлением `harness-lead` верни короткую сводку и сразу продолжай следующую
готовую задачу в согласованном объёме. Не создавай остановку ради подтверждения
успешного коммита. При настоящем препятствии сохрани `blocked` и точную причину.
Не меняй эталонные ответы вслед за неудачей без отдельного разрешения изменения
поведения; не сдавай незавершённую задачу и не обходи `record_attempt → stop`.
