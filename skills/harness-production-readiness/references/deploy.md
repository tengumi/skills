# Сборка, контейнер и выпуск

Читай только при `skill_mode=deploy`. Режим меняет материалы сборки, контейнера, CI и DevSecOps по согласованному составу процессов, а не выбирает архитектуру заново.

## Источники и подготовка

Прочитай текущую задачу, `AGENTS.md`, применимые `cicd.md`, `dev-setup.md`, документы архитектуры и команды, `team-patterns-production.md`, `production-applicability.md`. Шаблон задаёт структуру и технологии, пример сервиса — реализацию, пример выпуска — сборку и CI. Храни пути и роли источников раздельно, существенный конфликт оставь `OPEN` для решения владельцем.

1. Уточни согласованную форму: библиотека, CLI/исполняемый пакет, API, обработчик задач, планировщик или их сочетание.
2. Составь список деклараций/зафиксированных зависимостей, команд Makefile, точек входа, генерируемых клиентов, ресурсов, миграций и динамических импортов.
3. Сверь названия репозитория, сервиса, пакета, модуля, участника рабочей области, образа, задания CI, очереди и схемы БД.
4. Найди оставшиеся имена шаблона, но отдельно классифицируй доменные значения и названия внешних систем. Не делай глобальную замену.
5. Проверь разрешение на точные защищённые пути и зависимости. Используй уже записанное разрешение плана, не запрашивая повторно.
6. Проверь `verification_level`: обычная задача не повышает себя до `bundle`; полная цепочка принадлежит назначенному планом владельцу сборки.

Неизвестные базовый образ, библиотека CI, идентификаторы доступа/инвентаря, SM, имена секретов/монтирования или владелец схемы блокируют только зависящее исполняемое изменение. Заполнители не являются рабочими реквизитами. Внешние условия выпуска относятся к C.

## Реализация

Меняй только применимые файлы задачи: Dockerfile, настройки упаковки, Makefile, Jenkins/CI, DevSecOps, инструкцию выпуска. Не создавай универсальные файлы, если команда использует другой механизм. Сохраняй зависимости целевого агента; пример выпуска — материал сравнения, не замена его декларации.

Для готового результата докажи отдельно:

- зависимость установлена в чистом окружении сборки;
- статический и динамически загружаемый код попал в пакет;
- промпты, шаблоны, OpenAPI, токенизатор и другие применимые данные включены;
- Alembic `env.py` и `versions/` присутствуют, если нужны;
- каждый согласованный процесс запускается из самого пакета или образа.

Существования `dist/` и успешной сборки образа недостаточно.

## Проверки

Полная цепочка уровня `bundle` выполняется один раз после применимых изменений:

```text
Чистая установка → проверка импортов → принятые проверки → сборка
→ проверка состава готового результата → запуск процессов из него
```

Для wheel используй [`scripts/wheel_inventory.py`](../scripts/wheel_inventory.py) этого скилла: список ожидаемых путей и SHA-256 ресурсов берётся из исходного контракта, не из проверяемого архива. Для другого формата нужна его проверка содержимого, а не переименование в wheel. Установленный пакет запускай вне исходного репозитория.

Для короткой проверки локального процесса доступен [`scripts/process_smoke.py`](../scripts/process_smoke.py). Ожидаемый код завершения и освобождение ресурсов определяются фактическим приложением: `0` не универсален, а `-SIGTERM` не доказывает корректное завершение. Проверь закрытие порта, ресурсов и отсутствие принудительного убийства. Проверка через loopback не изолирует сеть процесса; внешние зависимости должны быть заменены или изолированы. Не запускай её через watcher в обход запрета сетевых команд.

Справка программ доступна через `--help`. Подставляй абсолютный путь к установленному скиллу, не текущему каталогу:

```bash
python "<harness-production-readiness>/scripts/wheel_inventory.py" "<готовый-пакет.whl>" --manifest "<ожидаемый-состав.json>"
```

Формат списка файлов и параметры запуска/остановки описаны в [инструкции проверок](runtime-checks.md); программы бери из локальной папки `scripts/` этого скилла. Они не устанавливают пакет, не выполняют развёртывание и не подтверждают выпуск автоматически.

При `capability` выполняй проверки изменённых файлов и своего слоя, не полную цепочку. Повторное использование результата допускается, когда его коммит — предок текущего `HEAD`, а изменения не затронули зависимости, ресурсы, упаковку, сборку и точки входа. Укажи исходный отчёт и различия, подтверждающие его актуальность; исходные ключи отчёта не переписывай.

Проверь применимые API, обработчик задач, планировщик и инициализацию БД отдельно. Запуск с миграциями разрешён только на явно разрешённой изолированной/принадлежащей проекту схеме либо в доказанном режиме без изменений. Не запускай его против неизвестной общей БД.

Перед передачей результата сверяй README и инструкцию сопровождения с реальными командами, настройками и ролями процессов. Исправь устаревшие инструкции демонстрационного каркаса в рамках задачи. Локальная проверка не доказывает работу в промышленной среде.

## Ограничения

- Не придумывай реквизиты, не записывай секреты, ключи, сертификаты или `.env`.
- Не меняй бизнес-логику и параметры LLM ради сборки.
- Не удаляй результаты генерации и рабочие данные вне явно разрешённой очистки.
- `files_hint` не является самостоятельным разрешением на защищённые файлы.
- Не включай реальные LLM/API/БД-вызовы в обычный CI без отдельного защищённого этапа и разрешения. Реальную внешнюю проверку ведёт `harness-eval` с `skill_mode=live`.
- Не закрывай готовность выпуска без требуемой установки и запуска готовых точек входа. Новую независимую проблему передай в пересмотр плана.
