# Выбор способа интеграции

Прочитай эту карту и только подходящий сценарий:

| Выбранный интерфейс | Инструкция |
|---|---|
| НОРМ REST с локальной генерацией из OpenAPI | [norm-rest.md](norm-rest.md) |
| MCP с подтверждёнными протоколом и операциями | [mcp.md](mcp.md) |
| API другого агента с опубликованным SDK владельца | [agent-api.md](agent-api.md) |

Имя класса `AgentApi` не определяет сценарий. Для другого интерфейса используй общие правила ниже и его контракт.

## Что является доказательством

Разделяй три источника:

- пример показывает способ решения; запиши его версию или её неизвестность;
- контракт целевой системы определяет операции, типы, ошибки, авторизацию и контекст;
- выполненная проверка целевого приложения показывает результат для конкретных SDK, версий и команды.

В секции `data-boundaries.md` достаточно ссылок на эту инструкцию, контракт и отличия реализации. Отсутствие отдельного примера или его коммита не требует остановки. Неизвестные существенные операция, авторизация или преобразование данных блокируют только зависимую реализацию: пример их не заменяет.

## Карта ответственности

```text
Типизированные настройки → создание клиента → регистрация зависимостей
                                                        ↓
Контекст запроса → поля/заголовки конкретной операции → использующий сервис
```

Укажи тип настроек, префикс, потребителя, регистрацию, время жизни объекта и соединения, владельца ресурса, открытие и ожидаемое закрытие. Это карта решений, а не требование отдельного файла на каждый пункт. Объекты запроса создаются при вызове; отдельная регистрация в контейнере для каждого DTO не нужна.

Сохраняй загрузчик шаблона команды. Если он использует Concoction/common, переиспользуй `init_config`/`ConfigurationProvider`; не вводи параллельный YAML/env-загрузчик. Для другого шаблона Concoction не навязывай. Правила объединения и проверки настроек бери из действующей версии библиотеки.

Один YAML и общий список регистраций допустимы. Разделять нужно типы настроек приложения, LLM, транспорта и независимых интеграций. Потребитель не получает все URL и секреты сервиса. Включённое подключение требует своего набора настроек; неверные обязательные настройки нельзя маскировать выключением.

Перед ручным клиентом проверь доступные пакеты проекта, общую библиотеку и разрешённые командные источники. Запиши выбор готового клиента либо причину ручного адаптера. Не требуется доказывать отсутствие SDK во всём мире. Прямой импорт SDK объявляется прямой зависимостью, а диапазон версий сверяется с API и установленной версией.

## Соединения, контекст и проверки

Внедряй клиент, функцию создания или сервис интеграции. Сессию можно открывать внутри операции адаптера, если владелец и закрытие явны. Общий HTTP-пул без состояния запроса может жить в `APP`; закрывает его владелец, не использующая обёртка. Асинхронное закрытие ожидается, включая ошибки и отмену.

Время жизни, протокол, префикс, повторы и раннее подключение определяет целевой контракт, не пример. Область `APP` сама по себе не разрешает сетевое соединение при запуске.

Арендатор, домен, сессия и идентификатор запроса берутся из конкретного контекста и передаются в указанные контрактом поля. Их взаимозаменяемость не предполагается; изменяемые заголовки арендатора нельзя хранить в общем клиенте. Сырые ответы не включай в исключения или обычные журналы.

Используй назначенные проверки блока и приложения: настоящий SDK и контейнер зависимостей, подмена только внешнего транспорта. Ожидаемые сетевые данные бери из независимого контракта/SDK/фикстуры владельца. Подмена, повторяющая придуманный код адаптера, подтверждает лишь внутреннюю согласованность. При общем клиенте проверь параллельные контексты. Общая проверка запуска должна реально выполняться принятой командой, а не существовать как исключённый файл.
