# Сохранение поведения: `prototype-parity`

Докажи, что целевой код сохраняет наблюдаемое поведение прототипа на одинаковых
логических входах. Способ передачи данных может меняться только после
разрешённого изменения подключения; смысл входа, результата, ошибок,
конечных состояний и внешних действий должен оставаться сравнимым.

## До запуска

- Назови путь и точную версию/хеш прототипа, версию целевого кода.
- Проверь весь план A с тем же `plan_id`: все остальные задачи завершены,
  их `evidence.commit_sha` входят в проверяемую версию, в том числе задачи,
  добавленные после составления первоначального списка зависимостей.
- Подготовь `prototype-contract.json` либо равноценный закреплённый контракт,
  хеши промптов, схем и настроек без секретов.
- Собери перечень безопасных входов из тестов, примеров и контракта.
  При отсутствии примеров создай минимальные синтетические данные с нужными
  схемами и важными граничными случаями.
- Зафиксируй правило сравнения: точное для детерминированных полей,
  обязательное совпадение схем/ошибок/конечных состояний; для модели —
  число повторов, обязательные поля и разброс обеих сторон.
- Внешний вызов требует отдельного разрешения и допустимой среды.
  Название этого режима разрешением не является.

## Проведение

1. Используй одинаковые логические входы; объясни допустимое преобразование
   между способами их передачи.
2. Для каждой системы отдельно зафиксируй статус/ошибку, обязательные поля,
   конечное состояние, внешние изменения и условие публикации результата.
3. Выполни обе стороны в сопоставимых условиях. Для структурированного ответа
   модели проверь вызываемый компонент, модель, `response_format`, непустые
   схему и имя, безопасную форму исходящего сообщения. Просьба «верни JSON»
   сама по себе структурированный ответ не гарантирует.
4. Сначала сравни точные поля, полноту схемы, решения/статусы, ошибки и условия
   завершения/публикации; только затем смысловую близость.
5. Для недетерминированного ответа сначала измерь разброс внутри каждой стороны,
   затем различие между сторонами. Не называй единичное различие регрессией,
   если сам прототип нестабилен.
6. Объясни каждое расхождение: дефект кода, допустимый разброс, согласованное
   преобразование, несовпадение данных/настроек либо неразрешённый конфликт.
7. Сохрани отчёт `docs/harness/evals/prototype-parity.md` и добавь его в
   подтверждения задачи. Результат ниже порога оставляет задачу незавершённой.

## Предел доказательства

Детерминированная проверка на безопасных примерах без сети может входить
в `make verify`; полный прогон качества с моделью выполняется отдельно.
Подменённые внешние ответы не доказывают чистую установку, сборку, рабочую
регистрацию зависимостей, ресурсы собранного пакета и реальные подключения.
Запуск настоящего приложения без сети проверяет
`harness-production-readiness:process`; реальную разрешённую систему — `live`.

В общий отчёт добавь `ported_from`, версии прототипа и цели, перечень входов,
преобразования передачи данных, хеши, таблицу полей/ошибок/конечных состояний,
число повторов и разброс каждой стороны, различия контракта либо явное
подтверждение их отсутствия.
