# Harness team kit

Канонический командный комплект для переноса прототипов AI-агентов в
production. Здесь лежит всё, что нужно для запуска и сопровождения Harness;
проектные прототипы, секреты и результаты конкретных прогонов сюда не входят.

## Быстрый старт

1. Подключить каталоги из `skills/` к совместимому Кодовому агенту принятым
   в команде способом. Перед обновлением сравнить существующие версии и не
   перезаписывать ручные изменения без review.
2. Настроить [`tasks-mcp`](mcp-servers/tasks-mcp/README.md).
   Все рабочие ветки Harness используют только формат
   `feature/<ID>[-short-description]` независимо от типа задачи. `ID` — ticket,
   если он уже указан, иначе `task.id`; Harness формирует короткое имя сам и не
   запрашивает Jira только ради ветки.
3. Создать target из официального team template и оставить prototype read-only.
   Если template не содержит полного `docs/harness/`, вручную скопировать только
   отсутствующие team docs, `templates/tasks.json`,
   `templates/data-boundaries.md` под именем `docs/harness/data-boundaries.md` и
   `PRE-INDUSTRIALIZATION-SPEC.md` под именем
   `docs/harness/pre-industrialization-spec.md`. Существующие target-файлы не
   перезаписывать; техническую карту заполняет Кодовый агент, не человек.
4. В `docs/harness/pre-industrialization-spec.md` указать прототип, описать
   своими словами будущие подключения и приложить доступные документы.
   Точные операции и настройки из этих документов агент извлечёт сам.
   Неизвестное можно оставить как `НЕИЗВЕСТНО`, данные о развёртывании —
   уточнить позже. Не включать значения секретов. Для заполнения с помощью
   агента есть отдельный подготовительный запрос в [ONBOARDING.md](ONBOARDING.md).
5. Прочитать [ONBOARDING.md](ONBOARDING.md) и запустить один entrypoint:

> Используй `$harness-lead`: prototype=`<path>`, target=`<path>`,
> team_template=`<path>`, team_docs=`<harness-kit/team-docs>` при отсутствии
> docs в template. Разрешаю безопасные офлайн-изменения внутри target, включая
> нужные manifest/lock и файлы шаблона. Работай автоматически до настоящего
> human checkpoint; прошлую реализацию этого агента не используй как источник
> кода.

`harness-watcher` нужен только там, где команды нельзя выполнять в среде агента
или это требует политика. Он не является обязательной частью каждого прогона.
Запрошенный pull работает fail-closed: при ошибке команды не запускаются на
старой копии, а отчёт фиксирует фактический source/lock/profile/commands key.
Watcher нельзя использовать для чтения значений env/`.env`/секретов;
типовые introspection-команды блокируются до выполнения.
В watcher 0.7.0 достаточно Python и стандартных shell/SSH-инструментов.
Встроенный фильтр отклоняет явные сетевые команды и удаление файлов;
`push`/`both` запрещены. Обычные тесты и сборка могут писать в локальное зеркало.
Это не ОС-песочница: действия внутри разрешённого скрипта фильтр не изолирует.
Зависимости нужно подготовить заранее; установка настроена на offline-режим.
Подробнее —
[защита и ограничения](harness-watcher/README.md).
Копирование kit не меняет разрешения открытого чата и не обновляет уже запущенный watcher.

| [`tools/runtime-checks/`](tools/runtime-checks/README.md) | состав wheel, контрольные суммы ресурсов и ограниченная проверка запуска/остановки процесса |
| [`tools/secret-guard/`](tools/secret-guard/README.md) | профиль запрета чтения секретных файлов и проверка песочницы на синтетических данных |
| [`evals/`](evals/README.md) | два замороженных учебных кейса, независимые проверки и повторяемое сравнение версий kit |
| [`integrations/jev-router/`](integrations/jev-router/README.md) | опциональный выбор модели кодового агента; закреплённый upstream и отдельный безопасный launcher |
| [`tools/goal-workers/`](tools/goal-workers/README.md) | эксперимент: пакет задачи, выбор модели и журнал native-субагентов внутри одной capability; ведущий сохраняет `/goal` и Tasks MCP |

Внешнее подключение можно реализовать после того, как техническая карта содержит
точную операцию, versioned contract, auth mechanism и проверяемый mapping.
Разрешение на live-вызов, изменение общей БД или deploy запрашивается отдельно
непосредственно перед рискованным действием.

Для подключения Harness выбирает командный/common/owner клиент, фиксирует цепочку
typed config → provider/factory → client → consumer и проверяет её через настоящую
production assembly. Один YAML допустим; общий config всех интеграций каждому
компоненту не передаётся. Предоставленный командный пример читается выборочно,
а его риски и версии не копируются автоматически. Контексты kit извлечены из
статического review и требуют проверки на SDK/контрактах текущего target.
Runtime-тест должен реально выполняться каноническим offline release/CI gate;
его наличие в исключённом каталоге не доказывает готовность.

Если общая сборка приложения ещё не создана, capability проверяет собственную
реальную factory/SDK; окончательное подключение доказывает единственный runtime
gate. Перенос sync→async и другие изменения механизма исполнения проходят
короткое review до submit. Проверка ресурсов установленного artifact и
актуальность README/runbook входят в существующий bundle/handoff, не создавая
новых подготовительных этапов.

## Выбор модели без отдельного API

После явного включения [режима субагентов](tools/goal-workers/README.md)
`harness-lead` использует локальные правила: механическая работа низкого риска →
fast, реализация по известному контракту → balanced, архитектура/review или
высокая неопределённость → strong. Модели берутся из доступного каталога;
модель ведущего не меняется. `tools/goal-workers/local-route.mjs` не обращается
к API роутера, не требует ключей и отклоняет настройки внешнего провайдера.
Независимые исполнители получают отдельные области файлов; общий результат
проверяет ведущий. Это не бесплатное выполнение моделей: остаются обычные
лимиты кодового агента. Ускорение всего маршрута этим режимом пока не доказано.

## Внешний Jev — отдельный эксперимент

Jev — необязательная надстройка над отдельным CLI-запуском. Он выбирает модель
кодового агента на новом пользовательском ходе и сохраняет её на продолжениях
tool-loop. Это **не переключение на каждой задаче Tasks MCP**, не замена
`harness-lead` и не изменение модели внутри опромышливаемого прототипа.
Один длинный `/goal` не гарантирует новое решение роутера на каждой внутренней
задаче. Подключение описано в [инструкции Jev](integrations/jev-router/README.md).

Классификатор TypeSafe получает текст запроса и метаданные маршрутизации.
Рабочие данные можно передавать только после согласования этого внешнего сервиса.
Защищённый Jev launcher kit отключает загрузку `.env`, полные дампы запросов/ответов
и автоматическую установку глобального скилла. Текущая сессия, глобальная
конфигурация и разрешения пользователя автоматически не меняются.
Ускорение и экономия пока не доказаны: их измеряют на одинаковом eval-кейсе
при сохранении обязательных проверок качества.

Для явно включённого сочетания `/goal` + субагенты есть отдельный
[режим делегирования](skills/harness-lead/references/routed-workers.md).
Ведущий остаётся на своей модели, а независимые части текущей задачи выполняют
субагенты с выбранной моделью. Локальная политика не требует TypeSafe;
внешний Jev по-прежнему разрешён только на синтетических данных. Этот режим
не подменяет provider текущего чата и не даёт субагентам собственные claims.
Результат исполнителя требует проверки, а журнал — не механизм песочницы ОС.

Происхождение восстановленных runtime-компонентов и границы достоверности
описаны в [PROVENANCE.md](PROVENANCE.md).

## Скиллы

Для полного прогона человек вызывает только `harness-lead`. Он
определяет текущее состояние по артефактам и передаёт следующий шаг нужному
скиллу. В `tasks.json` записывается точный исполнительный `use_skill` и, если
нужно, `skill_mode`.

### Управление процессом и контекст

- **harness-lead** — единая точка входа: сам определяет этап, выбирает
  следующую готовую задачу, ведёт перенос до настоящего решения человека и
  продолжает после паузы без новой сессии на каждую задачу.
- **harness-scan** — инвентаризирует workspace с несколькими репозиториями и
  показывает, какие из них готовы к Harness. Для уже выбранного target не нужен.
- **harness-context** — создаёт или безопасно обновляет `AGENTS.md` и
  `docs/harness/`, не перезаписывая командные документы и ручные правки.
- **harness-template** — разворачивает официальный шаблон команды; generic
  scaffold создаёт только для настоящего greenfield без team template.
- **harness-extract-patterns** — извлекает повторяющиеся архитектурные и кодовые
  соглашения из репозиториев, если официальной документации недостаточно.

### Этап A — перенос прототипа без потери логики

- **harness-source-analysis** — фиксирует фактическое устройство прототипа:
  функции, входы, схемы, prompts, LLM-параметры, retries, File IO и интеграции.
- **harness-ds-precheck** — сверяет прототип с правилами DS/MLE-кода и разделяет
  замечания на форму, изменение поведения и отдельные оптимизации; код не меняет.
- **harness-prototype-plan** — строит план этапа A из связанных проверяемых
  функциональных блоков, начиная с машинного контракта исходной логики; не
  дробит prompts, helpers и tests по числу файлов.
- **harness-prototype-port** — переносит одну часть прототипа в правильный слот
  team template, не меняя бизнес-логику, prompts, схемы и параметры моделей.

### Этапы B и C — production-доводка и выпуск

- **harness-extract-prod** — извлекает подтверждённые production-паттерны из
  team template, выбранного production-сервиса и release reference.
- **harness-production-plan** — определяет offline-срезы B и внешние
  release-гейты C; объединяет SDK/версию, lifecycle, adapter, DI и protocol tests одной внешней
  границы в capability-задачу вместо фиксированного списка T-101…T-120.
- **harness-production-readiness** — выполняет capability этапа B или C и отдельно
  доказывает настоящий `create_app`/`app`, production DI и lifespan без сети;
  unit-тест на фейковом приложении эту проверку не заменяет.
- **harness-team-layout-alignment** — приводит уже работающий сервис к структуре,
  именованию и форме кода команды без изменения его поведения.

### Выполнение и безопасность

- **harness-work-session** — выполняет одну задачу по циклу claim → реализация →
  проверки → commit → submit; в автоматическом прогоне не просит повторно
  выбрать задачу и использует назначенный уровень проверки.
- **harness-request-exec** — запускает команды через `harness-watcher`, когда
  безопасный локальный runtime недоступен; объединяет одну волну команд в один
  запрос. Exact execution key сохраняется; применимость старой проверки после
  несвязанных правок отдельно подтверждает `harness-pre-commit-check`.
- **harness-pre-commit-check** — проверяет конкретный diff перед коммитом:
  scope, назначенный уровень тестов, секреты, runtime-артефакты, защищённые
  файлы и соглашения команды, не повторяя полный build после каждой задачи.
- **harness-governance-gates** — добавляет постоянные repo/CI-защиты от секретов,
  запрещённых зависимостей и незадокументированного изменения логики прототипа.

### Golden и проверки

- **harness-golden** — создаёт и дорабатывает реалистичные эталонные наборы по
  примерам, контракту и источникам правильности; готовый spec не обязателен.
  Разделяет черновик для предметного просмотра и набор для оценки агента,
  независимо проверяет ответы и сохраняет происхождение cases.
- **harness-eval** — запускает проверки по уже определённому эталону в одном из
  режимов: `prototype-parity`, `golden` или разрешённая `live`-проверка.

`harness-golden` создаёт эталон, а `harness-eval` измеряет по нему качество.
Golden-контур необязателен для каждого опромышливания и не заменяет проверку
сохранения поведения прототипа.

Golden обновлён из рабочего проекта `harness-golden` 2026-10-16 (источник —
`harness-golden-vnext`, контрольные суммы в [PROVENANCE.md](PROVENANCE.md)).
Новый пакет содержит `run.json`, `cases.jsonl`, `audit.jsonl` и `results/` с
итоговой выдачей для человека. Есть структурный validator; его успех не доказывает
правильность эталонов. `business_review_draft` не используется как готовый
benchmark: `harness-eval:golden` принимает только выпущенный набор с подтверждением
нужных проверок и приёмки. Старые runs автоматически не переписываются.

## Источники истины

- `team-docs/` принадлежат команде и не переписываются skills;
- prototype и `prototype-contract.json` определяют сохраняемое поведение;
- `pre-industrialization-spec.md` хранит недостающие production-реквизиты и
  ссылки на официальные контракты; значения секретов в него не попадают;
- `data-boundaries.md` — техническая карта, которую Кодовый агент строит из
  прототипа, паспорта подключений и официальных описаний интеграций;
- versioned target contracts определяют новые API/tool/queue/DB boundaries;
- `tasks.json` хранит план, а tasks-mcp по умолчанию хранит lifecycle
  out-of-band;
- production neighbour и release reference дают evidence, но не становятся
  архитектурой target автоматически.

Перед распространением комплекта вручную проверить структуру skills, ссылки,
JSON-шаблоны и отсутствие локальных/runtime-артефактов.
