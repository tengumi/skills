# harness-watcher

`harness-watcher` — локальный мост для случаев, когда Агент работает с репозиторием
на удалённой машине, а команды нужно выполнить на рабочей станции команды.
Он читает файловую очередь через SSH/SCP, при необходимости переносит код через
`tar` поверх SSH, последовательно выполняет команды и возвращает JSON-отчёт.

> В 0.7.0 watcher использует простой фильтр запрещённых команд, без внешней
> песочницы и дополнительных CLI. Фильтр отклоняет явные сетевые команды,
> чтение секретов и удаление файлов. Это не изоляция ОС: он не может гарантировать,
> что разрешённый тест, скрипт или `make` не выполнит такие действия внутри.
> Запускайте только доверенный код и сначала проверьте рецепт на учебном проекте.

## Как устроен обмен

Удалённый репозиторий содержит три служебные папки:

```text
docs/harness/
├── exec-requests/   # входящие *.json
├── exec-reports/    # отчёты с тем же именем
└── exec-processed/  # обработанные запросы
```

Один цикл watcher:

1. Находит новый request на удалённой машине и скачивает его через SCP.
2. По `sync` переносит удалённую копию в `local_repo_root` через `tar` поверх SSH.
   Если запрошенный pull не удался, команды не запускаются: watcher возвращает
   error-report и завершает request.
3. Для сохранённого проекта подготавливает его окружение, если это разрешено
   при настройке. После sync/setup считает SHA-256 фактического дерева, затем запускает
   команды по очереди внутри `local_repo_root`. Перед запуском проверяет текст
   команд и hook; разрешённые команды запускает обычным shell без startup-файлов
   и без наследования произвольных переменных окружения ноутбука.
4. Стримит stdout/stderr в verbose-режиме и собирает ограниченный по размеру отчёт.
5. Фильтрует известный шум только в stdout успешных команд.
6. `push`/`both` отклоняются: команды не могут перезаписать удалённые файлы через sync.
7. Публикует report через SSH и перемещает request в `exec-processed/` без
   перезаписи существующего назначения. Для этого используется remote Python.

Фактический poller не использует `rsync`. Имя секции `[rsync]` сохранено для
совместимости старого формата конфига; её `exclude` применяется к tar-sync.
Поле `remote_rsync_available` в выводе `--check` — также legacy-диагностика и
не является требованием для работы watcher.

## Быстрый старт

Watcher требует Python 3.9+, `bash`, `ssh`, `scp` и `tar`;
на удалённой машине нужны `tar` и `python3` с POSIX file API. Служебные папки
requests/processed должны находиться на одной файловой системе. Ставить watcher через uv/pip и создавать ему
отдельную `.venv` не требуется. Команды ниже — из папки `harness-watcher`.

```bash
python3 watcher.py add contractors
python3 watcher.py start contractors --check
python3 watcher.py start contractors
```

Фильтр работает всегда, отдельно включать его не нужно. Старые параметры
песочницы и `--protected` принимаются для совместимости, но не включают изоляцию.
Сетевую установку зависимостей watcher не разрешает: `--sandbox-install-network`
не является способом её включить. Дополнительные меры —
[защита секретов](../tools/secret-guard/README.md).

### Что разрешено командам

- Запускать обычные команды проекта: `pytest`, `make test`, сборку и форматирование.
- Читать и менять локальную копию исходников, создавать build output и кеши.
- Использовать выделенный `TMPDIR` и окружение сервиса, подготовленное watcher.

### Что запрещено

- Явные сетевые команды, например `curl`, `wget`, `ssh` и `scp` в request.
  Служебный SSH/SCP самого watcher для очереди и отчётов работает отдельно.
- Явные команды удаления, например `rm`, `rmdir`, `unlink` и `find -delete`.
  Они запрещены для любых файлов: watcher не угадывает, кто создал файл.
- Известные команды чтения `.env`, ключей и значений переменных окружения.
- Обратная синхронизация `push` и `both`.

Фильтр не разбирает весь код проекта: сетевой вызов или удаление внутри
разрешённого Python-файла, теста или Makefile могут выполниться. Не используйте
его как защиту от недоверенного кода и не обходите отклонённую команду через helper.
Изменения локального зеркала и build output обратно не передаются — сохраняется
только ограниченный текстовый report. Временные результаты удаляются после команды.

Независимо от режима секретные пути исключаются из передачи и fingerprint.
Исключения нельзя снять пустым legacy-конфигом. Нефильтруемого SCP fallback
нет; включённые в дерево symlink/hardlink/специальные файлы блокируют sync.

Мастер один раз спросит SSH-хост, порт, путь к ключу, удалённый репозиторий и
способ установки зависимостей. Пути к зеркалу, окружению, очереди и журналу
назначаются автоматически. В следующий раз достаточно `start contractors`.
Для другого репозитория создайте другой профиль — править пути в TOML не нужно:

```bash
python3 watcher.py add another-agent --connection-from contractors
python3 watcher.py start another-agent
python3 watcher.py list
```

Подготовка **окружения сервиса**, не watcher:

- `uv`: выберите Python из шаблона и команду `uv sync --locked` с нужными
  командными группами/extras. Перед первым запросом watcher создаст внешнюю venv
  и установит зависимости. Изменились lock, manifests или указанные входы —
  установка повторится. Для подтверждённых editable-пакетов обычная правка
  Python-кода сама по себе её не запускает. Если локальная библиотека собирается
  в wheel или формат lock не удалось разобрать, учитываются также исходники.
- `command`: укажите локальный Python и команду команды, например `make install`.
  Она должна использовать подготовленную venv через `VIRTUAL_ENV` /
  `UV_PROJECT_ENVIRONMENT`, а не создавать `.venv` внутри зеркала. Здесь входом
  считается и код проекта: произвольная установка может собирать его в wheel.
- `none`: автоподготовка выключена, например для проекта без Python.

Установка разрешается один раз в мастере. Для неё задаются `UV_OFFLINE=1` и
`PIP_NO_INDEX=1`: пакеты/доверенный runtime нужно подготовить заранее вне watcher,
без передачи секретов агенту. Это режим установщика, не сетевой запрет ОС:
сборочный код и произвольный рецепт должны быть доверенными. `uv`, нужный Python
и проверенный SSH host key должны уже быть на машине;
watcher **не устанавливает глобальные инструменты и не скачивает Python**.
`--check`, `--status`, `list` и `add` зависимости не устанавливают.

Генерация и сборка могут писать в локальное зеркало, но не возвращают файлы
в удалённый репозиторий. Подготовка зависимостей не должна менять lock:
watcher проверяет его после установки. Проверки с реальными API, БД и секретами
не входят в этот сценарий; используйте офлайн-тесты с синтетическими данными.

Окружение лежит вне заменяемого зеркала. Проекты не делят venv, state или audit;
второй одновременный запуск того же профиля отклоняется. Два профиля для того же
хоста и удалённого пути создать нельзя. Это локальная защита, не распределённая
блокировка: не подключайте вторую машину или другой SSH-alias к той же очереди.
Ошибка установки
возвращает error-report без выполнения запроса. Полный вывод установки не
сохраняется и не отправляется агенту; в отчёте есть статус и безопасная причина.

Другие режимы и совместимость:

```bash
python3 watcher.py start contractors --once
python3 watcher.py start contractors --status
python3 watcher.py start contractors -v
python3 watcher.py --config /path/to/config.toml --check
python3 watcher.py --config /path/to/config.toml
```

Старые TOML-конфиги и `HARNESS_WATCHER_CONFIG` остаются читаемыми, но запуск должен
соответствовать новым ограничениям. Для pull используйте управляемый профиль:
watcher не должен очищать чужую директорию. Существующий репозиторий можно
проверять без sync, но запущенные команды способны его менять. Профили находятся в
`~/.config/harness-watcher/profiles/`, их данные — в соседней папке `projects/`.
Не переносите туда секреты. Полная настройка — [SETUP-GUIDE.md](SETUP-GUIDE.md).

### Обновление существующего watcher

Остановите старый процесс перед заменой файлов. Настройки уже запущенного
watcher и открытого чата автоматически не меняются. Дополнительный CLI больше
не нужен. Старые настройки песочницы можно убрать: они не обеспечивают изоляцию
в 0.7.0. Сохраните офлайн-рецепт установки и проверьте запуск на учебном проекте.

Старые непустые зеркало и venv без новой записи о владении не принимаются.
Не удаляйте их ради обновления: при остановленном watcher сохраните резервную
копию каталога данных профиля. Для перехода с версии без ownership-записей
переместите старые `repo/`, `venv/` и `environment.json` в отдельную резервную
папку. Оставьте на месте marker проекта, профиль, `state.json` и `audit.log`:
состояние очереди нельзя сбрасывать, иначе старые запросы могут выполниться снова.
Новые зеркало и venv создаст watcher. Не подделывайте ownership-файлы.
Для проверки уже существующего репозитория доступен TOML-режим без pull/setup.

Новые pull сначала загружаются в отдельную папку. Предыдущие собственные
зеркала сохраняются в `.harness-retained-*`, venv — в `venv-retained-*`.
Неудачные загрузки могут оставаться в `.harness-incoming-*`. Автоматической
очистки этих архивов нет: следите за местом и удаляйте ненужное самостоятельно
при остановленном watcher. Одновременное изменение его рабочих папок другими
процессами не поддерживается.

## Формат request

```json
{
  "request_id": "verify-001",
  "task_id": "T-001",
  "commands": [
    {"cmd": "python -B -m pytest -p no:cacheprovider -q", "cwd": "."}
  ],
  "timeout_seconds": 900,
  "stop_on_failure": true,
  "sync": "pull",
  "context": {
    "branch": "feature/T-001",
    "commit": "0123456789abcdef0123456789abcdef01234567",
    "purpose": "verify before commit",
    "verification_level": "bundle",
    "tree_fingerprint": "<ожидаемые 64 hex, если уже известны>",
    "lock_fingerprint": "<ожидаемые 64 hex или N/A, если уже известны>",
    "execution_profile": "<из прошлого observed report, если уже известен>",
    "commands_fingerprint": "<ожидаемые 64 hex, если уже известны>"
  }
}
```

Исполняются только `sync: "pull"` и `sync: "none"`. `push`, `both` и
`sync_after_exec=true` отклоняются. Если поле отсутствует, применяются настройки
конфига с теми же ограничениями. `cwd` обязан
оставаться внутри `local_repo_root`; выход через `..` блокируется.

Для новых запросов `request_id` должен соответствовать `[A-Za-z0-9._-]+`, а имя
файла обязано быть ровно `{request_id}.json`. Watcher сохраняет claim по
`request_id` **до** sync и запуска команд. Повторно появившийся ID никогда не
исполняется: существующий report сохраняется, request только переносится в
`exec-processed/`; если report отсутствует, создаётся terminal duplicate-error.
Повреждённый state также блокирует выполнение.

Переходная совместимость: старые ID с двоеточиями принимаются только если имя
файла совпадает с ними буквально. Преобразование `:` в `-` и другие неявные
нормализации запрещены, поскольку именно они могут создать две формы одного ID.
Новые requests всегда создавайте в каноническом формате без двоеточий.

В report из `context` возвращаются только безопасные координационные поля:
`branch`, `commit`, `source_revision`, `ticket`, `execution_mode`, `profile`,
`purpose`, `verification_level` и четыре `*_fingerprint` из примера. Остальные
поля отбрасываются. Секреты нельзя передавать даже в разрешённых полях.

`pre_exec_hook` выполняется перед каждой командой после `set -e`. Его удобно
использовать для PATH и активации подготовленного runtime, но не для
чтения секретов или обхода запретов. Hook также проверяется фильтром. Общий бюджет задаёт
`timeout_seconds`; отдельная команда дополнительно ограничена
`default_timeout_seconds`. После завершения и при таймауте watcher посылает
`TERM`, затем `KILL` оставшейся группе процессов команды. Это уборка обычных
дочерних процессов, а не гарантия против демонизации через `setsid`.

## Фильтрация и отчёты

- В `-v` виден живой поток stdout/stderr.
- В report сохраняются последние `stdout_max_chars` и `stderr_max_chars` символов.
- `sync` в report показывает фактический результат или запрет sync, а `source_snapshot`
  содержит вычисленный после sync `tree_sha256`, число файлов/байт. Git metadata
  не читается: `.git` исключён из передачи и fingerprint.
  Значение `context.commit` остаётся только заявленным контекстом и не считается
  доказательством проверенной ревизии.
- `evidence.observed` содержит фактически вычисленные `tree_fingerprint`,
  `lock_fingerprint`, `execution_profile` и `commands_fingerprint`.
  `evidence.requested_matches` сравнивает каждый из них с request и выставляет
  `all=true` только когда все четыре expected hints были переданы и совпали.
  Отсутствующий hint даёт `null`, а не ошибку; `false` означает реальное
  несовпадение и запрещает использовать запуск как evidence ожидаемого tree.
  Для будущего reuse сравнивают текущий требуемый key с `evidence.observed`,
  поэтому первый успешный запуск не нужно повторять только ради заполнения
  `execution_profile` в request.
- Content fingerprint всегда исключает `.git`, transport-папки
  `docs/harness/exec-{requests,reports,processed}`, venv, build output и типовые
  Python/Node cache-файлы. Поэтому появление report не меняет проверяемый hash.
- Lock fingerprint считается по известным dependency manifests/locks
  (`uv.lock`, `pyproject.toml`, requirements, Poetry/Pipenv, Node, Go и Cargo);
  при их отсутствии значение равно `N/A`.
- Execution profile — стабильный SHA-256 версии watcher/Python, безопасных
  execution-настроек, рецепта подготовки и отпечатка выбранного окружения. Сам `pre_exec_hook` и его
  значения в report не раскрываются.
- Поле `environment` в report показывает `ready`, `reused`, `disabled`,
  `maintenance` либо `error`. Это статус подготовки, не доказательство работоспособности сервиса.
- До запуска всей цепочки watcher отклоняет известные команды чтения значений:
  `env`/`printenv`, вывод `$VAR`, inline runtime environment dump, чтение или
  копирование `.env*`, `/proc/*/environ` и распространённые secret-store reads.
  В report возвращается только безопасная причина `secret-safety policy`, без
  исходной команды. `.env.example` тоже попадает под запрет. Косвенное чтение
  внутри разрешённого скрипта фильтр гарантированно не исключает.
- Regex-фильтр применяется только к stdout команд с exit code `0`.
- Для упавших команд regex-фильтр не применяется; при включённом `strip_ansi`
  удаляются только управляющие ANSI-последовательности.
- Если фильтр удалил бы весь полезный вывод, исходный stdout сохраняется.

на разрешённом удалённом стенде.

## Ограничения безопасности

- Pull разрешён только в принадлежащее watcher одноразовое зеркало; чужая
  директория не очищается. Храните важные файлы вне служебного зеркала.
- `sync_after_exec=true`, `push` и `both` запрещены. Report передаётся служебным
  каналом watcher, а не shell-командой агента.
- ОС-песочницы нет: разрешённый процесс получает обычные права пользователя
  watcher. Фильтр проверяет команду, но не ограничивает все действия её кода.
  Не запускайте watcher от администратора и держите рабочие секреты вне его среды.
- Проверка host key включена по умолчанию (`strict_host_key_checking=true`) и
  использует стандартный `known_hosts` OpenSSH либо явно заданный существующий
  `user_known_hosts_file`.
- Сначала получите fingerprint удалённого host key от доверенного владельца и
  проверьте его по независимому каналу. Не принимайте неизвестный ключ вслепую.
- `strict_host_key_checking=false` — явный высокорисковый opt-out только для
  изолированного теста; для командного и production-использования он запрещён.
- Не храните секреты в request, report, конфиге репозитория или audit log.
- Не используйте watcher для исследования значений окружения. Имена настроек
  берите из схемы или документации без секретов; `.env.example` тоже запрещён.
  Тесты используют синтетические значения. Live-тесты с секретами не входят
  в этот сценарий. Для строгого запрета сети и файловых операций нужна отдельная
  изоляция среды; фильтр текста команд её не заменяет.
- Это не классификатор содержимого: секрет в обычном `config.py` автоматически
  не распознаётся. Не допускайте секретов в доступном snapshot/runtime.
- Watcher должен принимать requests только из доверенного репозитория и SSH-контура.
