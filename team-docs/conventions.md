# Соглашения

## Структура репозитория

- Код объектно-ориентированный. Наборы функций, выполняющих один бизнес-сценарий (читай вызов эндпойнта) объединены в Классы-сервисы.
- Допускается разбиение классов-сервисов на несколько более маленьких классов для сложных сценариев.
- Допускается использование одиночных функций-утилит для технических задач. Они хранятся в папке `/utils`
- Все классы конструируются dishka-контейнером. Ручной вызов конструктора класса нежелателен.

## Обработка ошибок

- Если в коде произошла ошибка - он должен упасть. Обработка исключений, которая пытается замаскировать проблему, решить задачу другим способом или пропустить шаг, не допускается.
- Для обращений к внешним сервисам и llm в случае сетевых ошибок допускаются retry.

## Порядок работы

- Для проверки качетва кода запускается команда `make test` для запуска тестов и прогоняются `pre-commit` хуки для автоформатирования и выявления проблем
- Весь код должен быть покрыт юнит-тестами

## Зависимости

- Общий функционал для для всех сервисом вынесен в библиотеку `sberorm-agent-common`. Необходимо в первую очередь использовать функции оттуда, а не писать самому.

## Логирование

- Для объёмных отладочных выводов используется уровень `sber_orm_agent_common.logging.DEBUG_INFO` равный 15.
- Для менее объёмных логов, отражающих основные этапы работы приложения используется уровень INFO.

## VCS

- Все ветки для разработки, включая исправления, называются только по шаблону
  `feature/<Jira-id-задачи>-<кратко-суть-задачи>`. Другие префиксы не используются.
- Все комментарии к коммитам должны начинаться с <Jira-id-задачи>
